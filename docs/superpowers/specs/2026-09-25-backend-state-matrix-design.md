# state-matrix v2: матрица состояний бекенд-ручки

## Цель

Агент берёт **спеку одной HTTP-ручки** и строит матрицу: какие входы бывают, какие у них значения, какой ответ сервер даёт на каждое и **каким конкретным запросом** это проверить.

Каждая строка матрицы — готовый параметризованный тест-кейс: подготовка (данные в БД, ответы моков), запрос (сырой текст), ожидаемый ответ (статус, заголовки, тело), ожидаемые и **запрещённые** вызовы и записи.

Принципы:
- **агент зажат скриптом:** закрытые списки, ссылки проверяются, числа в фактах сверяются с текстом ссылок, значения, примеры и строки выводит код;
- **человек решает только то, что может решить:** механика скрипта принимается по умолчанию, человеку показываются отклонения и сводки;
- **незнание — тоже результат:** о чём спека молчит, не выдумывается, а становится строкой с мягким ожиданием и вопросом к аналитику.

Фронт (UI-состояния, деньги, инпуты) и база знаний удаляются полностью.

## Границы

- **Только HTTP-ручки с JSON.** gRPC, очереди, cron — вне охвата.
- **Материалы:** спека ручки; документы вокруг (другие спеки, OpenAPI в JSON, Jira/Confluence); схемы БД и миграции; конфиги и флаги; контракты внешних сервисов.
- **Код сервиса не читается.** Матрица описывает «как должно быть».
- **Одна модель — одна ручка.** Общие входы копируются из другой модели (`copy_from`).
- **Вне матрицы:** гонки и нагрузка — отдельный список со ссылками.
- **Не проверяем** инъекции и XSS, если спека не говорит о них явно.
- **Генерация кода тестов** — вне охвата; итоговый JSON для неё пригоден.

## Почему не полный перебор

Первая редакция перемножала все значения всех входов и резала результат правилами. На реальной ручке это даёт 10⁹ сочетаний, а правила сокращения начинают конфликтовать друг с другом: правило «не влияет» гасит условие соседнего правила, производный вход противоречит своим операндам, ошибки разных групп требуют порядка проверок, которого спека не знает.

Бекенд-ручка ведёт себя иначе, чем предполагает перебор: сервер останавливается на первой ошибке, а ответ почти всегда определяет **одно** отклонение от нормального запроса. Поэтому матрица строится так:

1. **обычная строка** — все входы в обычном значении;
2. **по одному отклонению** — для каждого необычного значения каждого входа одна строка, остальные входы обычные;
3. **явные сочетания** — только там, где спека говорит, что ответ зависит от пары входов (роль × статус заказа), по правилу «проверить сочетания».

Каждая строка полностью конкретна: пропусков «любое» нет, и из любой строки собирается исполнимый запрос. Число строк считается сложением, а не умножением.

## Модель

Файл `.states/models/<METHOD>_<path>.json`, `version: 2`. Модель v1 получает отказ «формат v1 не поддерживается».

### Шапка

`method`, `path`, `spec` (файл обязан существовать), `content_type` (по умолчанию `application/json`), `checklist` — ответы на чек-лист разведки (см. «Ход работы»).

### Классы значений

| Класс | Смысл | Примеры |
|---|---|---|
| **норма — вариант** | то же значение в другой форме; ответ совпадает с обычной строкой | «минимум», «максимум», «другое написание», «на повторе успех» |
| **норма — ветка** | корректное значение, которое может увести логику в другую ветку | другие значения списка, `false`, не-prod значение настройки, другие успешные исходы сервиса, «ни одной» у выборки, значения времени, значения полей записи в БД |
| **ошибка ввода** | не проходит валидацию по спеке | «нет поля» у обязательного, «больше максимума», битый JSON |
| **отказ** | ввод корректен, но сервер штатно отказывает или зависимость сбоит | «нет токена», «роль без доступа», «записи нет», «email занят», «таймаут» |
| **неизвестно** | спека молчит | ловушки без ответа |

Класс значений скрипта знает код; класс ловушек, добавок и значений полей записи указывает агент со ссылкой. Объединять можно только значения одного класса. Классы используются в ответах по умолчанию и в проверках назначений.

### Входы

| Поле | Значение |
|---|---|
| `name` | `body.items[].qty`, `storage.order`, `dep.pvz` — вложенность задаёт родителя |
| `source` | `path`, `query`, `header`, `body`, `caller`, `storage`, `dependency`, `config`, `clock`, `derived` |
| `type` | см. «Типы» |
| `facts` | факты типа, у каждого ссылка |
| `from` | откуда известен вход |
| `traps` | ответы агента на ловушки; неотвеченная — «спека молчит» |
| `extra` | добавки агента: `{value, class, examples, from}` |
| `example` | канонический пример обычного значения, со ссылкой; в обычной строке необязательные поля присутствуют |
| `copy_from` | `<модель>:<вход>` |

**Значения входа** = значения скрипта + ловушки «влияет» + добавки агента + служебные значения:
- **«обычное, другое написание»** — сюда уходят примеры ловушек, на которые агент ответил «не влияет» со ссылкой;
- **«спека молчит»** — сюда уходят примеры всех неотвеченных ловушек; класс «неизвестно».

**Ответ на ловушку:** «влияет» (класс и ссылка) → отдельное значение; «не влияет» (ссылка) → пример в «обычное, другое написание»; без ответа → пример в «спека молчит».

**Нормализация.** Пример «не влияет» хранит пару: что пришло и во что сервер это превращает (`as`). Шаблоны вызовов и ответа подставляют `as`. Если `as` неизвестно, в строке проверяется только факт вызова, а не его тело. Факт строки `trim` (со ссылкой) скрипт разбирает сам:
- «пробелы по краям» → «обычное, другое написание», `as` — обрезанное значение;
- «только пробелы» → ошибка ввода (как «пусто»);
- добавляется значение «максимум + пробелы по краям» (норма — вариант): длину часто проверяют до обрезки.

**Примеры.** Каждое значение хранит список примеров — параметры одного теста. Строка-отклонение параметризуется примерами **только своего** отклоняющегося значения; остальные входы берут канонический пример. Запросов на строку столько, сколько примеров у её отклонения.
- Примеры значений скрипта генерирует код из фактов: «больше максимума» при `max=100` → 101 символ латиницей и 101 кириллицей;
- примеры ловушек — механические, от кода;
- при `pattern` или `format` примеры минимума, максимума и канонический даёт агент, скрипт проверяет их против фактов;
- у добавок примеры обязательны; класс «норма» — пример обязан проходить факты.

**Объединение не теряет примеры:** «считать одинаковыми: нет поля, null, не строка, пусто, больше максимума» даёт одно значение «неверное» с пятью примерами — одна строка, пять запросов.

### Доверие

- Входы из `path`, `query`, `header`, `body` всегда без доверия.
- Гарантия снимает **только те значения, которые явно исключает**, и только по ссылке, которую понимает скрипт:

| Источник | Что скрипт разбирает | Что снимается |
|---|---|---|
| строка миграции | `NOT NULL`; `ENUM` / `CREATE TYPE … AS ENUM` | null; значения не из списка |
| JSON Schema ответа сервиса | `required`, `type`, `enum` | отсутствие поля, не тот тип, не из списка |

- Всё прочее (`CHECK`, диапазоны) — не гарантия; при желании агент предлагает объединение, человек принимает.
- Сбои вызова сервиса не снимаются никогда.
- Сборка сообщает, что снято и по какой ссылке.

### Встроенные входы

Скрипт добавляет их при `init`, агент заполняет факты.

**Запрос целиком.** Обычное: корректный запрос. Отклонения: битый JSON; не тот Content-Type; пустое тело; дубль ключа (класс «неизвестно»: многие разборщики JSON его молча принимают); тело больше лимита (при факте `max_body`); лишнее поле (факт `extra_fields`: запрещены → ошибка ввода, игнорируются → «обычное, другое написание», нет факта → «спека молчит»). У методов без тела: лишний параметр query, параметр дважды.

**Вызывающий** — если ручка закрыта. Факты: схема (`bearer`, `cookie`, `api_key`), роли. Обычное: роль с доступом. Отклонения: нет токена, неверный токен, просрочен, каждая роль без доступа.

**Ключ идемпотентности** — если спека его упоминает. Обычное: новый ключ. Отклонения: нет ключа; повтор после успеха с тем же телом; повтор после успеха с другим телом; повтор после ошибки. Факт `keep_on_error` — со ссылкой или «спека молчит». Подготовка строки-повтора включает первый запрос и его ответ.

### Встроенные строки

Кроме строк-отклонений скрипт добавляет:
- **минимальный запрос** — необязательные поля опущены, остальные на минимуме;
- **полный запрос** — все поля присутствуют, строки на максимуме, насколько позволяют производные входы;
- **две ошибки сразу** — только если в схеме ошибки есть массив полей: два разных поля неверны, ожидаются оба в ответе.

Первые две — «норма — вариант» и появляются, если у тела не меньше двух полей.

### Типы (`scripts/types.py`)

Названия значений человеческие и живут в коде. В модели хранятся внутренние id значений (`absent`, `max_plus`); ключи строк строятся из id.

| Тип | Факты | Обычное | Отклонения от скрипта | Ловушки |
|---|---|---|---|---|
| строка | min, max, unit (`chars`/`bytes`), required, nullable, pattern, format (`uuid`, `email`, `uri`, `date`), trim | обычное | нет поля, null, не строка, пусто, минимум, максимум, больше максимума, неверный формат (при `format`/`pattern`) | только пробелы, пробелы по краям, многобайтовые символы, управляющие символы, символы нулевой ширины, нормализация юникода, другой регистр |
| целое | min, max, required, nullable | обычное | нет поля, null, не число, дробное, меньше минимума, минимум, максимум, больше максимума | необычная запись числа (`1.0`, `1e2`, `-0`, больше 2⁵³), число строкой |
| число | min, max, precision, required, nullable | обычное | как у целого без «дробное», плюс «лишние знаки» при `precision` | необычная запись числа, число строкой |
| да/нет | required, nullable | `true` | нет поля, null, `false`, не true/false | «true» строкой, 0 или 1 |
| один из списка | values, required, nullable | первое значение | нет поля, null, остальные значения, не из списка | другой регистр, пробелы по краям |
| объект | required, nullable | обычный | нет поля, null, не объект, пустой объект | — |
| массив | min, max, unique, size (по умолчанию 2) | `size` обычных элементов | нет поля, null, пустой, минимум элементов, максимум элементов, больше максимума | повторы, один плохой элемент среди хороших |
| дата и время | min, max, format | обычное | нет поля, null, неверный формат, минимум, максимум | часовой пояс, 29 февраля, на границе «сейчас», переход на летнее время |
| запись в БД | entity, key, role (`lookup`/`unique`), soft_delete, owner, order | `lookup`: есть; `unique`: нет | `lookup`: нет; удалена (при `soft_delete`); чужая (при `owner`). `unique`: занято; занято удалённой записью (при `soft_delete`, класс по умолчанию «неизвестно») | — |
| выборка из БД | page_limit, order | несколько | ни одной, одна, ровно лимит страницы, больше лимита | — |
| настройка | values, prod | значение prod | остальные значения | — |
| время | — | обычное | значения, которые агент выделил из спеки (конец дня, граница акции) | — |
| внешний сервис | contract, ok, errors, retry, retry_on, order | первый успешный исход | остальные успешные исходы, каждая ошибка из контракта, другая 4xx, 5xx, таймаут, нет соединения; для класса из `retry_on` вместо одного значения два — «сбой, на повторе успех» и «сбой на всех попытках» | — |
| производный | expr | в пределах | зависят от выражения | — |

**Значения по источнику.** В `query` и `header` всё приходит строкой: у чисел и да/нет нет «не число» в смысле JSON-типа и ловушки «число строкой», зато есть «пустое значение» и «параметр дважды». Таблица применимости — в `types.py`.

**Вложенные поля.** Значение потомка ставится во все элементы массива. Отклонение родителя (нет поля, null, пустой) делает потомков неприменимыми — в этой строке их нет в запросе. Для ловушки «один плохой элемент среди хороших» плохой элемент получает первое значение класса «ошибка ввода» первого потомка, а без потомков — «не того типа».

**Поля записи в БД** — вложенные входы обычных типов с родителем-записью: `storage.order.status` (список), `storage.item.stock` (целое). Их значения попадают в `setup` записи; при «нет» или «удалена» у родителя они неприменимы. Класс значений полей записи агент задаёт со ссылкой; по умолчанию все, кроме обычного, — «норма — ветка».

**Класс отклонений записи в БД** — «отказ», кроме случаев, когда агент со ссылкой указывает иное.

**Производные входы** — закрытый набор:
- `len_concat(sep, skip_empty, limit, входы…)`: длина склейки против лимита (`limit` — число со ссылкой, сверяется как факт). Значения: в пределах (обычное), ровно лимит, больше лимита. Класс «больше лимита» агент указывает со ссылкой: ошибка ввода (проверяет наш сервер) или отказ (проверяет сервис); без ссылки — «спека молчит». `skip_empty` — со ссылкой или «спека молчит»; во втором случае вопрос в шаге 5.
- `compare(a, b)` для чисел: меньше, равно, больше (например `body.qty` против `storage.item.stock`). Класс каждого значения агент задаёт со ссылкой, без ссылки — «спека молчит».

Для каждой строки-отклонения производного входа скрипт **подбирает примеры операндов** в пределах их фактов (класс «норма»), так что выражение действительно даёт это значение. Эти примеры заменяют канонические примеры операндов в этой строке. Если подобрать нельзя — значение помечается «недостижимо» с объяснением («четыре поля по максимуму дают 326 символов, лимит 500») и уходит в шаг 5. Канонические примеры обязаны давать «в пределах»; иначе — ошибка при заведении.

**Пересчёт в каждой строке.** Отклонение соседнего входа может увести производный вход из пределов («qty — максимум» при запасе 10 фактически «больше запаса»). Поэтому после сборки каждой строки скрипт вычисляет все производные входы. Ушёл из пределов — скрипт подбирает неотклоняющиеся операнды внутри их фактов, чтобы вернуть «в пределах». Не получилось — строка помечается «противоречие: …» и автоматически не назначается.

**Место в цепочке.** Отклонение производного входа обнаруживается после чтения всех его операндов: его позиция — наибольший `order` среди операндов (для операндов из запроса — 0).

### Цепочка

Записи в БД, выборки и внешние сервисы стоят в одной шкале `order`: «читаем заказ (1) → зовём ПВЗ (2) → пишем заказ (3)». Одинаковый `order` — параллельные шаги. Цепочка задаётся фактами входов и показывается человеку одной схемой на шаге 2.

Цепочка определяет, что строка-отклонение **не трогает**: если отклонение обнаруживается на шаге N, все вызовы сервисов, записи и события после N попадают в `must_not`. Для ошибок запроса, вызывающего и параметров N = 0. Чтения из БД в `must_not` не попадают: тест не может надёжно проверить, что `SELECT` не было, а чтение по path-параметру законно идёт до валидации тела.

Порядок проверок между запросом, вызывающим и параметрами не моделируется: в строке всегда одно отклонение, а каким он будет при двух ошибках сразу — забота фреймворка. Если спека прямо задаёт такой порядок («401 раньше 400»), агент добавляет правило «проверить сочетания» для этой пары со ссылкой.

### Ответы

| Поле | Значение |
|---|---|
| `status` | целое 100–599 |
| `code` | код ошибки или пусто |
| `headers` | ключевые заголовки, шаблоны |
| `body` | шаблон тела: для 2xx — ключевые поля, для ошибок — схема ошибки |
| `effects` | **упорядоченный** список эффектов или явное «ничего» |
| `skips` | шаги цепочки, которые ответ сознательно пропускает, со ссылкой |
| `from` | ссылка |

**Эффект:** `db` `{entity, op: insert|update|delete|rollback|keep, fields: шаблон}`; `event` `{name, fields}`; `call` `{service, sends: шаблон}`. Число вызовов в строке скрипт берёт из длины списка ответов мока, а не из ответа: «на повторе успех» даёт 2, «сбой на всех попытках» — `retry` + 1.

**Шаблоны** ссылаются на входы по имени. Служебные подстановки: `{любой}` — поле генерирует сервер; `{поле_ошибки}` — имя входа, отклонившегося в строке (пусто у ошибок запроса и вызывающего). Скрипт подставляет примеры строки и получает ожидаемые вызовы, записи и тело.

**Моки сервисов:** агент даёт пример ответа по контракту на каждый успешный исход и каждую ошибку из `errors`; для 5xx, таймаута и отказа соединения мок генерирует скрипт. У значений с ретраями мок — **список ответов по попыткам**.

**Встроенные ответы «спека молчит»** — два, по природе отклонения:

| Ответ | Ожидание | Эффекты |
|---|---|---|
| «спека молчит — ввод» | статус не 5xx; если 4xx — тело по схеме ошибок | не проверяются, строка помечена «эффекты неизвестны» |
| «спека молчит — сбой сервиса» | статус не 2xx | записей не остаётся; шаги после N — в `must_not` |

**Ответы по умолчанию.** На шаге 1 агент задаёт соответствия со ссылкой, два уровня:
- **значение** → ответ: «вызывающий: нет токена → 401», «сервис ПВЗ: не найден → 404»;
- **входы + класс** → ответ: «поля тела (перечислены), ошибка ввода → 400 VALIDATION_ERROR».

Значение побеждает класс. Отдельным соответствием задаётся ответ **обычной строки**.

Скрипт назначает строкам с **одним** отклонением:
1. есть соответствие — по нему;
2. «норма — вариант» — ответ обычной строки;
3. иначе — встроенный «спека молчит»: для отклонений внешнего сервиса — «сбой сервиса», для остальных — «ввод». Такие строки уходят в вопросы шага 5.

«Норма — ветка» без соответствия **не наследует** успех: она получает «спека молчит — ввод» и попадает в отдельный блок сводки «ветки — проверь».

Строки с двумя и более отклонениями (сочетания, «две ошибки сразу») автоматически **не назначаются никогда**: сочетание заводится ради приоритета, и ответ на него даёт спека, а не механика. Руками агент назначает сочетания и переопределяет автоматику со ссылкой.

### Правила

Встроенного (обычная строка, по одному отклонению, неприменимость потомков, цепочка) хватает на большинство ручек. Правил три:

| Вид | В чате | Поля | Что делает |
|---|---|---|---|
| `merge` | считать одинаковыми | `input`, `values`, `into` | значения одного класса → одно значение со всеми примерами |
| `combine` | проверить сочетания | `inputs` (2–3), `values?` | добавляет строки со всеми сочетаниями отклонений этих входов (или перечисленных значений); остальные входы обычные |
| `forbid` | не бывает | `when` | убирает строки-сочетания, которых не бывает |

У каждого правила ссылка. `merge`, предложенный при заведении входа, показывается и принимается вместе со входом. `combine` нужен, только когда спека говорит, что ответ зависит от пары: роль × статус заказа, флаг × ветка, порядок «401 раньше 400». Строки сочетаний назначаются только руками.

### Сборка

1. Применить объединения.
2. Обычная строка.
3. Для каждого входа, для каждого значения, кроме обычного, — строка-отклонение. Потомки отклонившегося родителя неприменимы. Производные — с подбором операндов.
4. Встроенные строки.
5. Строки «проверить сочетания».
6. «Не бывает».
7. Пересчёт производных входов в каждой строке; «противоречие» там, где подобрать нельзя.
8. Автоназначение.

**Потолок — 100 строк.** Выше — разбивка, какой вход и какое сочетание сколько добавляет.

**Строка итога:**

| Поле | Содержание |
|---|---|
| `id` | стабильный: 8 hex от ключа строки (`вход=id значения` отклонений); коллизии проверяются при сборке |
| `name` | имя теста из человеческих названий: «регион — больше максимума → 400 VALIDATION_ERROR» |
| `setup` | записи в БД (поля по `key` и фактам; «остальные поля — из фабрики теста»), моки по попыткам, настройки, время, первый запрос (для повтора ключа) |
| `request` | метод, путь, заголовки, **тело сырым текстом**; по одному на каждый пример отклонения |
| `expect` | статус, заголовки, тело по шаблону |
| `calls` | ожидаемые вызовы с телом и числом раз |
| `writes` | ожидаемые записи и события |
| `must_not` | шаги цепочки, которых строка не должна касаться |

Ключ строки зависит только от её отклонений, поэтому правка одного входа не меняет id строк других входов.

Тело запроса собирается собственным сериализатором с «сырыми» вставками: дубль ключа, битый JSON, `1e2`, `-0`, большие числа сохраняют исходное написание.

### Назначение и проверки

Ответы по умолчанию закрывают большинство строк. Остаток агент назначает пачкой `[{outcome, rows, ref}]`; ссылка обязательна и проверяется. Назначение хранится по ключу строки. Если ключ исчез, назначение перечисляется как осиротевшее.

| Проверка | Уровень |
|---|---|
| отклонение — ошибка ввода, а ответ 2xx | предупреждение |
| отклонение класса «норма — вариант», а ответ 4xx | предупреждение |
| отказ на шаге N, а в эффектах нет шага N | предупреждение |
| в эффектах шаг после N, и его нет в `skips` | предупреждение |
| отказ сервиса после записи в БД, а у записи нет `rollback` или `keep` | предупреждение «что стало с записью до сбоя?» |
| ответ ошибки сервиса не из `retry_on`, а мок описан несколькими попытками | ошибка модели |
| текст по ссылке назначения не содержит ни статуса, ни кода | предупреждение |
| минимум или максимум дают другой ответ, чем обычное | информация |

### Ссылки

| Вид | Проверка |
|---|---|
| `file.md:§2.1` | раздел с номером из текста заголовка существует |
| `file:"текст"` | текст есть в файле |
| `file:line` | строка существует; **для `.md` запрещена** — только раздел или цитата |
| `file.json#/json/pointer` | указатель разрешается |
| `https://… "цитата"` | цитата обязательна; «не проверена». Рекомендуется сохранить страницу в `.states/sources/` |
| свободный текст | «не проверена»; пустая — нет |

**Сверка факта со ссылкой.** Числа (`min`, `max`, `max_body`, `page_limit`, `retry`, `limit`) ищутся в тексте по ссылке **как отдельные токены**; списки (`values`, `errors`, роли) — поэлементно. Не нашлось — предупреждение при показе входа. Пересказ словами человек подтверждает вручную.

**Дрейф.** При принятии сущности скрипт запоминает отпечаток фрагмента по каждой ссылке: раздел, цитату, строку. Фрагмент изменился или пропал — сущность снова «ждёт решения» с пометкой «источник изменился».

`status` всегда показывает долю непроверенных ссылок.

### Принятие и сбросы

У ответов, ответов по умолчанию, входов (с их объединениями), правил, чек-листа и матрицы есть статус **«ждёт решения» / «принято»**. Сборка применяет только принятое.

| Что изменилось | Последствие |
|---|---|
| вход, правило | строки этого входа или правила пересобираются; их назначения живут, пока жив ключ; принятие матрицы снимается |
| ответ | его строки помечаются «проверить»; принятие матрицы снимается |
| источник по ссылке | сущность → «ждёт решения» |
| исходная модель у `copy_from` | ничего: копия независима |
| добавлен ответ на шаге 4 | снимается только принятие матрицы |

**Повторное принятие матрицы показывает только разницу** с прошлым принятием: новые, исчезнувшие и изменившиеся строки. Матрицу нельзя принять при осиротевших назначениях, строках без ответа и пометках «проверить».

## Ход работы

| Шаг | Что происходит | Решения человека |
|---|---|---|
| **0 · Разведка** | агент читает материалы и отвечает на **чек-лист** скрипта: авторизация и роли, владение данными, записи в БД и проверки уникальности, выборки, внешние сервисы, порядок шагов, ретраи, идемпотентность, флаги, зависимость от времени, лимиты размера. На каждый пункт — «есть» со ссылкой или «в материалах нет». Без полного чек-листа входы заводить нельзя | 1 |
| **1 · Ответы** | каталог ответов и ответы по умолчанию; скрипт предлагает стандартные для встроенных входов (битый JSON, 415, 413, 401, 403), если спека их упоминает | 1 |
| **2 · Входы** | параметры запроса — **одной таблицей**, по строке на поле; вызывающий, записи и сервисы — по одному, цепочка — схемой. Показываются только отклонения от механики: ловушки «влияет» и «не влияет», добавки, предупреждения сверки, снятое по гарантии, «спека молчит», предложения объединить | 3–5 |
| **3 · Сочетания** | только если спека говорит о зависимости от пары входов | 0–2 |
| **4 · Матрица** | сводка «ответ → сколько строк и имена тестов»; отдельными блоками — «ветки — проверь», назначенные руками, с предупреждениями, «противоречие» и «недостижимо» | 1 |
| **5 · Пробелы** | вопросы к аналитику: «спека молчит», недостижимые значения, `skip_empty`, `keep_on_error`, непроверенные ссылки; проверки вне матрицы | — |

**Итог:** `.states/runs/<ручка>.json` со строками итога и `.states/runs/<ручка>.questions.md` — вопросы к аналитику с номерами.

**Повтор после ошибки** у ключа идемпотентности: первый запрос — строка «сбой на всех попытках» первого сервиса по цепочке, а без сервисов — первая ошибка ввода.

**Ответы аналитика.** Пользователь приносит ответы; агент правит ловушки и факты через `input`. Пересобираются только строки затронутых входов, повторное принятие показывает только разницу.

## Инструменты MCP

Имена без префикса. Повторный вызов с тем же id перезаписывает запись (с последствиями по таблице), `remove: true` удаляет.

| Инструмент | Назначение |
|---|---|
| `init` | шапка и чек-лист; добавляет встроенные входы |
| `outcome` | ответ или ответ по умолчанию |
| `input` | вход, пачка входов (параметры) или `copy_from`; возвращает значения с классами и примерами, отклонения, предупреждения, число строк до и после |
| `rule` | правило; возвращает строк было и станет |
| `approve` | список сущностей или «матрица» |
| `build` | сборка; возвращает сводку по ответам, предупреждения, осиротевшие, недостижимые |
| `assign` | пачка назначений; возвращает новые предупреждения |
| `rows` | строки по фильтру: без ответа, с предупреждением, по ответу, по входу, изменённые с прошлого принятия; `full=true` — строки итога целиком |
| `status` | шаг, счётчики, «ждёт решения», предупреждения, непроверенные ссылки, чего не хватает |

**Запреты в коде:** входы до полного чек-листа; правило на несуществующий вход или значение; объединение значений разных классов; `assign` до `build`; принятие матрицы при осиротевших, неназначенных и «проверить».

**Формат ответов** — компактный JSON без markdown, тексты человеческие, все ошибки вызова одним списком. Описания инструментов — 1–2 строки, подробности в SKILL.md.

## Эталонный пример: поиск ПВЗ

**Спека (пишется в `examples/pvz-search-spec.md`):** `POST /pvz/search`, без авторизации. Тело: `region`, `settlement`, `street` — строки 1..100, `house` — строка 1..20, все обязательны. Пробелы по краям обрезаются. Любая ошибка поля → `400 VALIDATION_ERROR` с полем. Лишние поля запрещены → 400. Тело до 16 КБ → иначе 413. Content-Type не `application/json` → `415`. Тело пустое или не разбирается как JSON → `400 BAD_JSON`. Адрес склеивается через «, »; если длиннее 255 символов → `400 ADDRESS_TOO_LONG`. Поиск — `GET /pvz?address=…` сервиса ПВЗ: 200 с ПВЗ → наш 200 с адресом; 404 → наш `404 PVZ_NOT_FOUND`; 429 → наш `503 PVZ_BUSY`; 5xx и таймаут — один повтор, потом `502 PVZ_UNAVAILABLE`.

**Модель:** у полей факт `trim` (§ «пробелы по краям обрезаются»); объединение «неверное»; ответы по умолчанию — обычная строка → 200; поля тела, ошибка ввода → 400 VALIDATION_ERROR; битый JSON и пустое тело → 400 BAD_JSON; Content-Type → 415; больше 16 КБ → 413; лишнее поле → 400 VALIDATION_ERROR; длина адреса больше 255 → 400 ADDRESS_TOO_LONG; ПВЗ: не найден → 404, 429 → 503, 5xx и таймаут на всех попытках → 502.

**Воронка, посчитанная руками:**

| Источник строк | Значения-отклонения | Строк |
|---|---|---|
| обычная строка | — | 1 |
| запрос целиком | битый JSON, не тот Content-Type, пустое тело, дубль ключа, больше 16 КБ, лишнее поле | 6 |
| каждое из 4 полей | неверное (нет поля, null, не строка, пусто, только пробелы, больше максимума — 6 примеров), минимум, максимум, другое написание (пробелы по краям, `as` — обрезанное), максимум + пробелы по краям, спека молчит (многобайтовые, управляющие, нулевой ширины, нормализация, регистр) | 4 × 6 = 24 |
| длина адреса | ровно 255, больше 255 (поля по максимуму дают 326 — достижимо) | 2 |
| сервис ПВЗ | не найден, 429, другая 4xx, 5xx — на повторе успех, 5xx на всех попытках, таймаут — на повторе успех, таймаут на всех попытках, нет соединения | 8 |
| встроенные строки | минимальный запрос (все поля на минимуме — необязательных нет), полный запрос (поля на максимуме, последние укорочены скриптом до 255 по длине адреса); «две ошибки сразу» нет — в схеме ошибки одно поле | 2 |
| **итого** | | **43** |

**Пересчёт производного входа** в строках-отклонениях полей ничего не меняет: одно поле по максимуму (100 или 102 до обрезки) с каноническими остальными даёт адрес меньше 255.

**Автоназначение — 43 из 43:**

| Как назначено | Строки | Сколько |
|---|---|---|
| ответ обычной строки | обычная | 1 |
| «норма — вариант» наследует 200 | минимум, максимум, другое написание, максимум + пробелы у 4 полей; ровно 255; на повторе успех (вызов 2 раза — по моку); минимальный и полный запрос | 16 + 1 + 2 + 2 = 21 |
| соответствие по классу | неверное у 4 полей → 400 VALIDATION_ERROR | 4 |
| соответствие по значению | 5 значений запроса; больше 255; не найден (ветка); 429; два «на всех попытках» | 5 + 1 + 1 + 1 + 2 = 10 |
| «спека молчит — ввод» | «спека молчит» у 4 полей; дубль ключа | 5 |
| «спека молчит — сбой сервиса» | другая 4xx, нет соединения | 2 |

**Решения человека:** чек-лист 1, ответы с соответствиями 1, поля одной таблицей 1, запрос 1, длина адреса 1, сервис ПВЗ 1, матрица 1 — **7**.

**Строка «найден»:** запрос `{"region":"Московская область","settlement":"Химки","street":"Ленина","house":"5"}`, вызов `GET /pvz?address=Московская область, Химки, Ленина, 5` один раз, ответ 200 с адресом из примера контракта; `must_not` пуст.

**Строка «регион — другое написание»:** запрос с `"  Московская область  "`, ожидаемый вызов с обрезанным значением.

**Строка «длина больше 255»:** операнды подобраны скриптом (например, `region` 100, `settlement` 100, `street` 50, `house` 3 символа); `must_not`: вызов ПВЗ.

**Строка «5xx на всех попытках»:** мок `[500, 500]`, вызов 2 раза, ответ 502.

**Вопросы шага 5:** ловушки полей без ответа; дубль ключа в JSON; другая 4xx и отказ соединения у ПВЗ; запятая внутри поля (`street = "Ленина, 5"`) — её агент добавляет сам как вопрос к склейке.
