# state-matrix v2: матрица состояний бекенд-ручки

## Цель

Агент берёт **спеку одной HTTP-ручки** и строит матрицу: какие входы бывают, какие у них значения, какие сочетания различимы, какой ответ сервер даёт на каждое и **каким конкретным запросом** это проверить. Агент максимально зажат скриптом: закрытые списки, обязательные ссылки, проверка фактов по тексту ссылок, базовые значения и примеры выводит код, а не агент.

Результат полезен, только если по нему можно сразу писать тесты. Поэтому каждая строка матрицы — это готовый тест-кейс: подготовка, запрос, ожидаемый ответ, ожидаемые вызовы.

Фронт (UI-состояния, деньги, инпуты) и база знаний удаляются полностью.

## Границы

- **Только HTTP-ручки с JSON.** gRPC, обработчики очередей, cron — вне охвата.
- **Входные материалы:** спека ручки; документы вокруг неё (другие спеки, OpenAPI в JSON, Jira/Confluence); схемы БД и миграции; конфиги, флаги, контракты внешних сервисов.
- **Код сервиса не читается.** Матрица описывает «как должно быть», а не «как сделано».
- **Одна модель — одна ручка.** Общие входы (авторизация, пагинация) копируются из другой модели.
- **Вне матрицы:** гонки (два одновременных запроса), нагрузка. Агент выписывает их отдельным списком со ссылками.
- **Не проверяем** SQL-инъекции и XSS как отдельные варианты, если спека не говорит о них явно.

## Модель

Файл `.states/models/<METHOD>_<path>.json`, поле `version: 2`. Модель v1 при загрузке получает отказ «формат v1 не поддерживается»; миграции нет.

### Шапка

`endpoint`: `method`, `path`, `spec` (файл спеки, обязан существовать), `content_type` (по умолчанию `application/json`).

### Одобрение — единое для всего

Всё, что решает человек, имеет статус **«ждёт решения» / «принято»**: ответы, входы (вместе с их объединениями), правила, матрица целиком. Любая правка сущности возвращает её в «ждёт решения». Сборка применяет только принятые входы и правила; матрица готова, только когда принято всё.

### Входы

| Поле | Значение |
|---|---|
| `name` | уникальное имя: `body.items[].qty`, `storage.order.status`, `dep.pvz` |
| `source` | закрытый список: `path`, `query`, `header`, `body`, `caller`, `storage`, `dependency`, `config`, `clock` |
| `type` | закрытый список, см. «Типы» |
| `facts` | факты типа; у **каждого** факта своя ссылка |
| `from` | ссылка, откуда известен сам вход |
| `contract` | ссылка на гарантию; если есть и проходит проверку — вход **доверенный** |
| `traps` | ответ на **каждую** ловушку типа: влияет (и допустимо ли) или не влияет, со ссылкой |
| `extra` | добавки агента: `{value, valid, example, from}` |
| `example` | пример обычного значения из спеки, со ссылкой |
| `normal` | какое значение считать обычным для правила «проверять по одному»; по умолчанию см. «Типы» |
| `copy_from` | `<модель>:<вход>` — взять вход из другой модели целиком; всё равно требует одобрения |

**Значения входа = значения от скрипта + ловушки «влияет» + добавки агента.** Групп у входа нет. Сливать значения можно только правилом «считать одинаковыми».

**Допустимость.** Каждое значение помечено «допустимое» или «недопустимое» (прошло бы валидацию по спеке). Для значений скрипта это знает код, для ловушек и добавок — агент при заведении. Допустимость используется в автоматических проверках, в сравнениях и в правиле «проверять по одному». Объединять можно только значения одной допустимости.

**Пример на каждое значение.** Скрипт генерирует конкретный пример для своих значений из фактов и `example`: «минимум» при `min=2` → `"Мо"`, «больше максимума» при `max=100` → 101 символ, «не строка» → `42`. Если у строки есть `pattern`, примеры для минимума, максимума и обычного даёт агент, а скрипт проверяет их против `pattern`, длины и диапазона. У добавок агента пример обязателен и тоже проверяется: заявлено «допустимое» — пример обязан проходить факты.

**Доверие:**
- Входы из `path`, `query`, `header`, `body` всегда недоверенные.
- `dependency` и `config` доверенные, если есть `contract` со ссылкой.
- `storage` доверенный, только если ссылка ведёт на **ограничение в схеме**: строка по ссылке содержит `NOT NULL`, `CHECK`, `UNIQUE`, `REFERENCES`, `ENUM` или `CREATE TYPE`. Описание поля в документации гарантией не считается: старые данные и `varchar` без ограничения его нарушают.
- Доверенный вход получает только допустимую по контракту часть значений, ловушек у него нет.
- У внешнего сервиса сбои вызова остаются всегда: контракт гарантирует форму ответа, а не сам ответ.
- Сборка сообщает, что отброшено по контракту: вход, значения, ссылка.

### Встроенные входы

Скрипт добавляет их сам при `init`, агент заполняет факты. Без них нельзя собрать матрицу.

**Запрос целиком** (`request`). Значения:

| Значение | Когда есть |
|---|---|
| обычный | всегда |
| битый JSON | у методов с телом |
| не тот Content-Type | у методов с телом |
| пустое тело | у методов с телом |
| лишнее поле | всегда; факт `extra_fields`: запрещены / игнорируются, со ссылкой. Если спека молчит — вопрос человеку |
| дубль ключа в JSON | у методов с телом |
| тело больше лимита | если есть факт `max_body` |
| лишний параметр в query | у методов без тела |

**Вызывающий** (`caller`), если ручка закрыта. Факты: схема (`bearer`, `cookie`, `api_key`), роли, есть ли тенанты. Значения: нет токена, неверный токен, просрочен, у каждой роли без доступа — «роль X», чужой тенант (если есть тенанты), обычный.

**Ключ идемпотентности**, если спека его упоминает. Значения: нет ключа, новый ключ, повтор с тем же телом, повтор с другим телом. Для «повтор» подготовка строки включает первый запрос.

### Типы (`scripts/types.py`)

Названия значений и ловушек **сразу человеческие** и живут в коде: скрипт отдаёт их готовыми.

| Тип | Факты | Значения от скрипта | Ловушки |
|---|---|---|---|
| строка | min, max, required, nullable, pattern | нет поля, null, не строка, пусто, минимум, максимум, больше максимума, обычное | только пробелы, пробелы по краям, многобайтовые символы, управляющие символы, символы нулевой ширины, нормализация юникода, другой регистр |
| целое | min, max, required, nullable | нет поля, null, не число, дробное, меньше минимума, минимум, максимум, больше максимума, обычное | ноль, отрицательное, `1.0`, `1e2`, `-0`, больше 2⁵³, число строкой |
| число | min, max, precision, required, nullable | нет поля, null, не число, меньше минимума, минимум, максимум, больше максимума, обычное | ноль, отрицательное, `1e2`, `-0`, лишние знаки после запятой, больше 2⁵³, число строкой |
| да/нет | required, nullable | нет поля, null, true, false, не true/false | «true» строкой, 0 или 1 |
| один из списка | values, required, nullable | нет поля, null, каждое значение, значение не из списка | другой регистр, пробелы по краям |
| массив | min, max, unique, item (тип элемента) | нет поля, null, пустой, минимум элементов, максимум элементов, больше максимума | повторы, один плохой элемент среди хороших |
| дата и время | min, max, format | нет поля, null, неверный формат, минимум, максимум, обычное | часовой пояс, 29 февраля, на границе «сейчас», переход на летнее время |
| запись в БД | entity | есть, нет, удалена, чужая | — |
| выборка из БД | page_limit | ни одной, одна, несколько, ровно лимит страницы, больше лимита | — |
| сравнение двух входов | left, right, op | меньше, равно, больше, не сравнивается | — |
| настройка | values, prod (значение в prod) | каждое значение; не-prod помечены «не prod» | — |
| внешний сервис | contract, ok (успешные исходы словами), errors (коды из контракта), retry (сколько повторов), order (место в цепочке вызовов) | каждый успешный исход, каждая ошибка из контракта, другая 4xx, 5xx, таймаут, нет соединения; при `retry` ещё «сбой, на повторе успех» | — |

Внутренние ключи типов в API (`string`, `int`, `ref` …) видит только агент.

**Правила вывода значений:**
- `required=false` → «нет поля» допустимое; `nullable=true` → «null» допустимое;
- граничные значения — только при заданных `min`/`max`;
- обычное по умолчанию: «обычное», «есть», «несколько», «равно», значение prod, первый успешный исход;
- **сравнение** зависит от своих входов: если хоть один из них недопустим, скрипт сам ставит «не сравнивается». Строки «поля нет, но сумма длин больше лимита» не существуют;
- **вложенные поля** (`body.items[].qty`) описывают значение поля во всех элементах массива; случай «один плохой элемент среди хороших» — ловушка массива.

### Ответы

| Поле | Значение |
|---|---|
| `id` | внутренний, в чат не выходит |
| `status` | целое 100–599 |
| `code` | код ошибки из спеки или пусто |
| `returns` | для 2xx — шаблон ключевых полей тела: `{"address": "{dep.pvz.address}", "id": "{любой}"}` |
| `effects` | список эффектов **или** явное «ничего» |
| `from` | ссылка |

**Эффект** — одно из:
- `db: <что>` — запись, изменение, удаление, откат;
- `event: <имя>`;
- `call: <сервис>` с шаблоном `sends`: `"{body.region}, {body.settlement}, {body.street}, {body.house}"`.

Шаблоны ссылаются на входы по имени. Скрипт подставляет примеры значений строки и получает **ожидаемый вызов и ожидаемое тело ответа** для каждой строки. Так проверяется не только куда ушёл запрос, но и что именно ушло и вернулось. Для полей, которые сервер генерирует сам, есть `{любой}`.

Для внешнего сервиса агент даёт пример успешного ответа по контракту на каждый успешный исход; `{dep.pvz.address}` берётся из него.

### Цепочка вызовов

Внешние сервисы в модели упорядочены фактом `order`. Скрипт проверяет назначения:
- строка, где сервис N сбоит, получает ответ с эффектом `call: N`;
- в такой строке нет вызовов сервисов с большим `order`, если ответ этого не объясняет;
- если до сбоя были записи в БД или вызовы, у ответа должен быть явный эффект про них: «откат», «компенсация» или «остаётся». Иначе предупреждение «что стало с записью до сбоя?».

### Правила

| Вид | В чате | Смысл | Поля |
|---|---|---|---|
| `merge` | считать одинаковыми | значения входа ведут себя одинаково → одно значение, пример берётся первый | `input`, `values`, `into`, `when?` |
| `forbid` | не бывает | комбинация невозможна | `when` |
| `independent` | проверять по одному | среди входов группы не больше одного отличается от обычного | `inputs`, `when?` |
| `irrelevant` | не влияет | при условии входы не влияют на ответ | `when`, `inputs` |

Условие `when` — `{вход: [значения]}`, все пары должны совпасть; допускается `{вход: "допустимое"}` и `{вход: "недопустимое"}`. Значения берутся после безусловных объединений.

У каждого правила ссылка `from`.

### Сборка

Порядок фиксирован и не зависит от порядка добавления:

1. **Безусловные «считать одинаковыми»** сжимают оси.
2. **Безусловные «проверять по одному»** заменяют входы группы одной составной осью: все обычные плюс каждое необычное значение каждого входа по отдельности. Размер оси — 1 + Σ(nᵢ − 1) вместо Πnᵢ. Группы не пересекаются: вход в двух безусловных группах — ошибка.
3. **Подсчёт** строк формулой. Для воронки считается и сырое число (без правил), но оно не перебирается. Больше 1 000 000 после шагов 1–2 — отказ с разбивкой, какой вход сколько даёт.
4. **Перебор.**
5. Условные «считать одинаковыми».
6. Автоматическое «не сравнивается» у сравнений.
7. «Не бывает».
8. Условные «проверять по одному».
9. «Не влияет»: у строки в «любое» уходят входы из **всех** сработавших правил; условия сверяются с исходной строкой.
10. Дедупликация по ключу строки.

**Потолок — 100 строк.** Выше — блок с разбивкой, какой вход сколько добавляет.

**Пример строки.** Для каждой строки скрипт собирает: запрос (метод, путь, заголовки, тело JSON из примеров значений с учётом вложенности; «нет поля» — ключ опущен, «любое» — обычное значение), подготовку (состояние БД, ответы внешних сервисов, настройки, время — фразами), ожидаемый ответ (статус, код, тело по шаблону), ожидаемые вызовы (по шаблонам `sends`).

### Назначение ответов

Агент ставит ответ строкам пачкой `[{outcome, rows, ref}]`; ссылка обязательна и проверяется. Назначение хранится по ключу строки (`вход=значение|…`) и переживает пересборку.

**Осиротевшие назначения.** Если после правки ключ строки исчез, сборка перечисляет старые назначения с ответами. Матрица не готова, пока каждое не переназначено или не снято.

**Автоматические проверки назначений** — предупреждения, которые агент обязан показать человеку:

| Проверка | Почему это подозрительно |
|---|---|
| в строке есть недопустимое значение, а ответ 2xx | неверные данные прошли |
| все значения допустимы, все сервисы успешны, а ответ 4xx | верный запрос отвергнут |
| строки отличаются только граничным и обычным значением одного входа, а ответы разные | граница обычно ведёт себя как норма; если нет, спека должна это говорить |
| текст по ссылке назначения не содержит ни статуса, ни кода ответа | ссылка, скорее всего, не про этот ответ |
| нарушена цепочка вызовов | см. «Цепочка вызовов» |

### Ссылки

| Вид | Проверка |
|---|---|
| `file.md:§N` | раздел существует |
| `file:"текст"` | текст есть в файле |
| `file:line` | строка существует |
| `file.json#/json/pointer` | указатель разрешается (для OpenAPI в JSON) |
| `https://… "цитата"` | цитата обязательна; ссылка помечается «не проверена». Агенту рекомендуется сохранить страницу в `.states/sources/` и ссылаться на файл — тогда она проверяется |
| свободный текст | допускается, помечается «не проверена»; пустая ссылка — нет |

**Сверка факта со ссылкой.** Для числовых фактов (`min`, `max`, `max_body`, `page_limit`, `retry`) число должно встречаться в тексте по ссылке; для списков (`values`, `errors`, роли) — каждый элемент. Не нашлось — предупреждение «в §2.1 нет числа 1000», которое агент показывает при одобрении входа. Это ловит опечатки и выдуманные числа, но не пересказ словами («до ста символов») — тогда человек подтверждает вручную.

**Дрейф источников.** При одобрении сущности скрипт запоминает отпечаток фрагмента по каждой её ссылке (раздела, строки или цитаты), а не всего файла. Если фрагмент изменился или пропал, сущность возвращается в «ждёт решения» с пометкой «источник изменился». Правки в других разделах спеки ничего не сбрасывают.

**Счётчик непроверенных ссылок** всегда есть в `status`: человек видит, какая доля модели держится на тексте, который скрипт не смог проверить.

## Ход работы

| Шаг | Что происходит | Что принимает человек |
|---|---|---|
| **0 · Разведка** | агент читает разрешённые материалы и показывает опись: входы по источникам, ответы, внешние сервисы по порядку вызова | опись полная или что добавить |
| **1 · Ответы** | каталог ответов с эффектами и шаблонами | каталог целиком |
| **2 · Входы** | по одному: значения с примерами, ловушки, добавки, предупреждения сверки, **предложение объединений** | вход вместе с объединениями |
| **3 · Правила** | «проверять по одному», «не влияет», «не бывает», условные объединения — по одному, у каждого эффект в строках | каждое правило |
| **4 · Матрица** | сборка, назначение ответов со ссылками, разбор предупреждений и осиротевших назначений | матрицу целиком |
| **5 · Пробелы** | вопросы к спеке без ответа, проверки вне матрицы (гонки), счётчик непроверенных ссылок | — |

Ответы идут до входов, чтобы предложения объединений опирались на готовый каталог. Объединение, принятое на шаге 2, можно отменить на шаге 3; скрипт покажет, сколько строк вернётся.

**Итог работы:** `.states/runs/<ручка>.json` — все строки с подготовкой, запросом, ожидаемым ответом и вызовами. Из него пишут тесты руками или генератором; генерация кода тестов — вне охвата.

## Инструменты MCP

Имена без префикса: сервер добавляет `state-matrix`. Повторный вызов с тем же id перезаписывает запись и возвращает её в «ждёт решения», `remove: true` удаляет.

| Инструмент | Назначение | Проверки |
|---|---|---|
| `init` | ручка; добавляет встроенные входы | спека существует |
| `outcome` | ответ | статус 100–599, формат эффектов, шаблоны ссылаются на существующие входы, ссылка |
| `input` | вход или `copy_from` | закрытые списки, ссылка у каждого факта, сверка фактов, ответ на каждую ловушку, примеры против фактов, доверие. Возвращает значения с примерами и допустимостью, число строк до и после |
| `rule` | правило | входы и значения существуют, объединяются значения одной допустимости, безусловные группы не пересекаются. Возвращает строк было и станет |
| `approve` | список сущностей или «матрица» | сущности существуют; матрицу нельзя принять при осиротевших назначениях и строках без ответа |
| `build` | сборка | см. «Сборка» |
| `assign` | пачка `[{outcome, rows, ref}]` | ответ есть, строки есть, ссылка; возвращает новые предупреждения |
| `rows` | строки по фильтру: без ответа, с предупреждением, по ответу, по входу; `example=true` — с примерами | — |
| `status` | шаг, счётчики, «ждёт решения», предупреждения, непроверенные ссылки, чего не хватает до готовности | — |

**Запреты в коде:** правило на несуществующий вход или значение; `assign` до `build`; принятие матрицы с незакрытыми назначениями.

### Формат ответов инструментов

Компактный JSON, без markdown. Колонки называются один раз, строки идут массивами. Значения и тексты ошибок — человеческие.

```
{"ok":true,"input":"body.region","values":[["нет поля",false,null],["минимум",true,"Мо"],...],"rows":{"raw":729,"now":729},"warnings":["в §2.1 нет числа 100"]}
{"ok":false,"errors":["не ответил про ловушки: «только пробелы», «пробелы по краям»","у максимума длины нет ссылки"]}
```

Все ошибки вызова — **одним списком**, чтобы агент исправил их за один повтор. Описания инструментов — 1–2 строки; подробности в SKILL.md.

## Язык для пользователя

Пользователь скилла не знает внутренностей. **Всё, что видно в чате, — простыми словами.**

| Внутри | В чате |
|---|---|
| `merge`, `irrelevant`, `independent`, `forbid` | «считать одинаковыми», «не влияет», «проверять по одному», «не бывает» — с объяснением в одну строку |
| статусы | «ждёт твоего решения» / «принято» |
| пропуск в строке | «любое» |
| id ответов, строк, правил | не показываются: ответ — статусом и кодом, строка — номером по порядку, правило — фразой |
| доверенный вход | «по контракту пустым не бывает — эти случаи не проверяем» |
| источники | «из тела запроса», «из базы», «ответ сервиса ПВЗ» |
| инструменты, JSON, поля модели | никогда |

Человеческие названия лежат в `scripts/types.py` и приходят готовыми. SKILL.md содержит эту таблицу и запрет выводить внутренние обозначения.

## Скилл (SKILL.md)

- шаги 0–5 с воротами «принято»; формат «Шаг N из 5 · …»;
- перед любым вопросом агент показывает **все** данные, о которых спрашивает, таблицей, рядом — счётчики из `status`;
- вопросы всегда с вариантами ответа;
- `approve` — только после явного «да» в чате;
- предупреждения скрипта показываются все, без отбора;
- никаких внутренних обозначений;
- отказ работать по коду сервиса.

## Эталонный пример: поиск ПВЗ

`POST /pvz/search` принимает `region`, `settlement`, `street`, `house`, склеивает их через запятую и ищет ПВЗ через `GET /pvz?address=…` соседнего сервиса. Спека и контракт пишутся в `examples/` при реализации; точные числа воронки фиксируются в `test_engine` после этого.

Ожидаемая форма результата:
- входы: запрос целиком, четыре поля, сравнение «длина склеенной строки ≤ лимита сервиса ПВЗ», сервис ПВЗ (найден, не найден, 429, 5xx, таймаут, нет соединения);
- правила: объединение недопустимых значений каждого поля; «проверять по одному» для запроса и полей; «не влияет»: при недопустимом запросе или поле ответ сервиса не важен; при сбое сервиса значения полей не важны (условие: все поля допустимы);
- порядка 25 строк; у строки «найден» ожидаемый вызов `GET /pvz?address=Московская область, Химки, Ленина, 5` и тело `{"address": …}` из примера контракта.

Пример обязан поднять вопросы в шаге 5: ответ клиенту при 4xx от ПВЗ; разделитель внутри поля (`street = "Ленина, 5"`); «не найден» — 404 или пустой 200; обязательность `settlement`; один ПВЗ или список.

## Что держится только на инструкции

- что «принято» сказал человек, а не агент;
- что агент показал данные и предупреждения полностью;
- что ссылка понята верно, а не просто существует и содержит нужное число;
- что опись на шаге 0 полная: входа, о котором агент не узнал, в матрице не будет.
