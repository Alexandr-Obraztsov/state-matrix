# state-matrix v2: матрица состояний бекенд-ручки

## Цель

Агент берёт **спеку одной HTTP-ручки** и строит матрицу: какие входы бывают, какие у них значения, какие сочетания различимы, какой ответ сервер даёт на каждое и **каким конкретным запросом** это проверить.

Каждая строка матрицы — готовый параметризованный тест-кейс: подготовка (данные в БД, ответы моков), запрос (сырой текст), ожидаемый ответ (статус, заголовки, тело), ожидаемые и **запрещённые** вызовы и записи.

Два принципа:
- **агент зажат скриптом:** закрытые списки, ссылки проверяются, числа в фактах сверяются с текстом ссылок, значения и примеры выводит код;
- **человек решает только то, что может решить:** механика скрипта принимается по умолчанию, человеку показываются отклонения. Цель на типичной ручке (POST, 8 полей, одна сущность в БД, один внешний сервис, авторизация) — **не больше 12 решений человека**.

Незнание — тоже результат: всё, о чём спека молчит, не выдумывается, а становится строкой с ожиданием «не 5xx» и вопросом к аналитику.

Фронт (UI-состояния, деньги, инпуты) и база знаний удаляются полностью.

## Границы

- **Только HTTP-ручки с JSON.** gRPC, очереди, cron — вне охвата.
- **Материалы:** спека ручки; документы вокруг (другие спеки, OpenAPI в JSON, Jira/Confluence); схемы БД и миграции; конфиги и флаги; контракты внешних сервисов.
- **Код сервиса не читается.** Матрица описывает «как должно быть».
- **Одна модель — одна ручка.** Общие входы копируются из другой модели (`copy_from`).
- **Вне матрицы:** гонки и нагрузка — отдельный список со ссылками.
- **Не проверяем** инъекции и XSS, если спека не говорит о них явно.
- **Генерация кода тестов** — вне охвата; итоговый JSON для неё пригоден.

## Модель

Файл `.states/models/<METHOD>_<path>.json`, `version: 2`. Модель v1 получает отказ «формат v1 не поддерживается».

### Шапка

- `method`, `path`, `spec` (файл обязан существовать), `content_type` (по умолчанию `application/json`);
- `checklist` — ответы на обязательный чек-лист разведки (см. «Шаг 0»);
- `check_order` — порядок проверок (см. «Порядок проверок»).

### Классы значений

Каждое значение любого входа относится к одному из трёх классов:

| Класс | Смысл | Примеры |
|---|---|---|
| **норма** | запрос корректен, сервер идёт дальше | «обычное», «минимум», «есть», «найден», «не prod» |
| **ошибка ввода** | не пройдёт валидацию по спеке | «нет поля» у обязательного, «больше максимума», битый JSON |
| **отказ** | ввод корректен, но сервер штатно отказывает или зависимость сбоит | «нет токена», «роль без доступа», «записи нет», «чужая», «таймаут», «5xx» |

Класс значений скрипта знает код. Класс ловушек и добавок указывает агент. Классы используются в условиях правил (`{вход: "ошибка ввода"}`), в порядке проверок, в автоматических проверках назначений и в объединении: **объединять можно только значения одного класса**.

### Входы

| Поле | Значение |
|---|---|
| `name` | `body.items[].qty`, `storage.order.status`, `dep.pvz` — вложенность задаёт родителя |
| `source` | `path`, `query`, `header`, `body`, `caller`, `storage`, `dependency`, `config`, `clock`, `derived` |
| `type` | см. «Типы» |
| `facts` | факты типа, у каждого ссылка |
| `from` | откуда известен вход |
| `traps` | ответы агента на ловушки; неотвеченная ловушка = «спека молчит» |
| `extra` | добавки агента: `{value, class, examples, from}` |
| `example` | пример обычного значения со ссылкой |
| `parent` | для БД — явно (`storage.order.status` → `storage.order`); для вложенных полей выводится из имени |
| `key` | для записи в БД — вход запроса, который её адресует (`body.order_id`) |
| `copy_from` | `<модель>:<вход>` |

**Значения входа = значения скрипта + ловушки «влияет» + добавки агента + одно значение «спека молчит»**, в которое скрипт собирает все неотвеченные ловушки как параметризованные примеры. У входа нет групп: сливать значения можно только правилом «считать одинаковыми».

**Ответ на ловушку** — одно из трёх:
- «влияет»: класс и ссылка — ловушка становится отдельным значением;
- «не влияет»: ссылка — ловушка уходит примером в значение «обычное»;
- «спека молчит» (по умолчанию, без ссылки) — пример в значении «спека молчит».

**Примеры.** Каждое значение хранит **список** примеров — это параметры одного теста:
- для значений скрипта примеры генерирует код из фактов: «больше максимума» при `max=100` → 101 символ латиницей и 101 символ кириллицей;
- для ловушек примеры механические, тоже от кода;
- если у строки есть `pattern` или `format`, примеры для минимума, максимума и обычного даёт агент, а скрипт проверяет их против фактов;
- у добавок агента примеры обязательны и проверяются: класс «норма» — пример обязан проходить факты.

**Объединение не теряет примеры.** «Считать одинаковыми: null, не строка, пусто» даёт одну строку матрицы с тремя примерами. Строк меньше, тестов столько же, стоят они как один параметризованный.

### Доверие

- Входы из `path`, `query`, `header`, `body` всегда без доверия.
- Гарантия снимает **только те значения, которые явно исключает**, и только со ссылкой, которую понимает скрипт:

| Источник гарантии | Что скрипт умеет разобрать | Что снимается |
|---|---|---|
| схема БД (строка миграции) | `NOT NULL`; `CHECK (col op число)`; `ENUM`/`CREATE TYPE … AS ENUM` | null; значения вне диапазона; значения не из списка |
| контракт сервиса (JSON Schema ответа в файле) | `required`, `type`, `enum`, `minLength`/`maxLength`, `minimum`/`maximum` | отсутствие поля, не тот тип, не из списка, вне диапазона |

- `CHECK … NOT VALID` и `REFERENCES … ON DELETE SET NULL` гарантией на соответствующее значение не считаются.
- Сбои вызова сервиса снимаются никогда: контракт гарантирует форму ответа, а не сам ответ.
- Сборка сообщает, что снято и по какой строке гарантии.

### Встроенные входы

Скрипт добавляет их при `init`, агент заполняет факты.

**Запрос целиком.** Значения: обычный; битый JSON; не тот Content-Type; пустое тело; дубль ключа; тело больше лимита (при факте `max_body`); лишнее поле (факт `extra_fields`: запрещены → «ошибка ввода», игнорируются → «норма», молчит → «спека молчит»). У методов без тела вместо телесных: лишний параметр query, параметр дважды.

**Вызывающий** — если ручка закрыта. Факты: схема (`bearer`, `cookie`, `api_key`), роли. Значения: нет токена, неверный токен, просрочен, каждая роль без доступа, обычный. Чужие данные моделируются значением «чужая» у записи в БД, а не у вызывающего.

**Ключ идемпотентности** — если спека его упоминает. Значения: нет ключа; новый ключ; повтор после успеха с тем же телом; повтор после успеха с другим телом; повтор после ошибки. Факт `keep_on_error` (хранится ли ключ после сбоя) обязателен или «спека молчит». Повторы комбинируются только с полностью обычной строкой; подготовка строки включает первый запрос и его ответ.

### Типы (`scripts/types.py`)

Названия значений человеческие и живут в коде. Внутренние id значений (`absent`, `max_plus`) хранятся в модели; ключи строк строятся из id, названия нужны только для показа.

| Тип | Факты | Значения от скрипта | Ловушки |
|---|---|---|---|
| строка | min, max, unit (`chars`/`bytes`), required, nullable, pattern, format (`uuid`, `email`, `uri`, `date`) | нет поля, null, не строка, пусто, минимум, максимум, больше максимума, неверный формат (при `format`/`pattern`), обычное | только пробелы, пробелы по краям, многобайтовые символы, управляющие символы, символы нулевой ширины, нормализация юникода, другой регистр |
| целое | min, max, required, nullable | нет поля, null, не число, дробное, меньше минимума, минимум, максимум, больше максимума, обычное | необычная запись числа (`1.0`, `1e2`, `-0`, больше 2⁵³), число строкой |
| число | min, max, precision, required, nullable | как у целого, без «дробное», плюс «лишние знаки после запятой» при `precision` | необычная запись числа, число строкой |
| да/нет | required, nullable | нет поля, null, true, false, не true/false | «true» строкой, 0 или 1 |
| один из списка | values, required, nullable | нет поля, null, каждое значение, не из списка | другой регистр, пробелы по краям |
| объект | required, nullable | нет поля, null, не объект, пустой объект, обычный | — |
| массив | min, max, unique | нет поля, null, пустой, минимум элементов, максимум элементов, больше максимума | повторы, один плохой элемент среди хороших |
| дата и время | min, max, format | нет поля, null, неверный формат, минимум, максимум, обычное | часовой пояс, 29 февраля, на границе «сейчас», переход на летнее время |
| запись в БД | entity, key | есть, нет, удалена, чужая | — |
| выборка из БД | page_limit | ни одной, одна, несколько, ровно лимит страницы, больше лимита | — |
| настройка | values, prod | каждое значение; не-prod помечены «не prod» | — |
| внешний сервис | contract, ok, errors, retry, retry_on, order | каждый успешный исход, каждая ошибка из контракта, другая 4xx, 5xx, таймаут, нет соединения; при `retry` на каждый класс из `retry_on`: «сбой, на повторе успех» и «сбой на всех попытках» | — |
| производный | expr (см. ниже) | зависят от выражения | — |

**Значения по источнику.** Для `query` и `header` всё приходит строкой: у чисел и да/нет нет значений «не число» в смысле JSON-типа и ловушки «число строкой», зато есть «пустое значение» и «параметр дважды». Таблица применимости значений по источнику — в `types.py`.

**Обычное по умолчанию:** «обычное», `true`, первое значение списка, «есть», «несколько», значение prod, первый успешный исход.

**Производные входы** — закрытый набор выражений:
- `len_concat(sep, входы…)` — длина склейки; значения «≤ лимита», «лимит ровно», «больше лимита»;
- `compare(a, b)` — сравнение двух входов (числа, даты); значения «меньше», «равно», «больше».

Для каждого значения производного входа скрипт **подбирает примеры операндов** в пределах их фактов и проверяет, что выражение от них действительно даёт это значение. Эти примеры заменяют примеры операндов в строке. Если подобрать нельзя (четыре поля по 100 символов не превысят лимит 500), значение помечается «недостижимо» с объяснением. Это тоже находка.

**Автоматические «нет родителя» и «не вычисляется».** Если родитель — «нет поля», null, пустой массив, «нет» или «удалена», все его потомки получают «нет родителя». Если хоть один операнд производного входа не в классе «норма», производный вход получает «не вычисляется». Строк «пустой массив × плохой элемент» и «записи нет × статус отменён» не существует.

### Порядок проверок

`check_order` — порядок групп: **запрос → вызывающий → параметры (path, query, header, body) → БД → сервисы** (внутри сервисов — по `order`). Это порядок по умолчанию. Агент меняет его только со ссылкой; если спека молчит, порядок по умолчанию остаётся и уходит в вопросы шага 5.

`config`, `clock` и производные входы в порядке не участвуют: они не «падают», а меняют поведение.

**Сворачивание по порядку — автоматически.** В строке находится первая по порядку группа, где есть значение класса «ошибка ввода» или «отказ». Все входы **последующих** групп уходят в «любое»: сервер до них не дошёл. Внутри группы параметров ошибок несколько сразу не бывает: они сворачиваются правилом «проверять по одному», встроенным для этой группы.

Это заменяет большую часть ручных правил «не влияет» и снимает вопрос «401 или 400 при двух ошибках сразу» — ответ задан порядком, а порядок — одна сущность, которую человек принимает один раз.

### Ответы

| Поле | Значение |
|---|---|
| `status` | целое 100–599 |
| `code` | код ошибки или пусто |
| `headers` | ключевые заголовки ответа (`Location`, `Retry-After`), шаблоны |
| `body` | шаблон тела: для 2xx — ключевые поля, для ошибок — схема ошибки, включая поле, на которое она указывает (`{"field": "{поле}"}`) |
| `effects` | **упорядоченный** список эффектов или явное «ничего» |
| `skips` | сервисы, которые этот ответ сознательно не вызывает, со ссылкой |
| `from` | ссылка |

**Эффект** — одно из:
- `db`: `{entity, op: insert|update|delete|rollback|keep, fields: шаблон}`;
- `event`: `{name, fields: шаблон}`;
- `call`: `{service, sends: шаблон, times: число или «по ретраям»}`.

**Встроенный ответ «спека молчит»** — ожидание «не 5xx, тело по схеме ошибок». Скрипт сам назначает его строкам, где единственное отклонение от нормы — значение «спека молчит».

Шаблоны ссылаются на входы по имени, `{любой}` — для генерируемых сервером полей. Скрипт подставляет примеры строки и получает ожидаемый вызов, запись и тело ответа.

**Моки сервисов:** агент даёт пример ответа сервиса по контракту на каждый успешный исход и на каждую ошибку из `errors`; для 5xx, таймаута и отказа соединения мок генерирует скрипт.

### Правила

Встроенного (сворачивание по порядку, «нет родителя», «не вычисляется», «проверять по одному» для параметров) хватает на большинство ручек. Правила нужны для бизнес-специфики.

| Вид | В чате | Поля |
|---|---|---|
| `merge` | считать одинаковыми | `input`, `values`, `into`, `when?` |
| `forbid` | не бывает | `when` |
| `independent` | проверять по одному | `inputs`, `when?` |
| `irrelevant` | не влияет | `when`, `inputs` |

`when` — `{вход: [значения] | "класс"}`, все пары должны совпасть; значения — после безусловных объединений. Объединение, предложенное при заведении входа, и правило `merge` — одна сущность: она показывается и принимается вместе со входом.

**Правило не может сбросить в «любое» вход, на котором стоит условие любого сработавшего в этой строке правила.** Такой вход остаётся. Иначе строка «поле неверное, сервис в таймауте» превратилась бы в строку с обычными примерами и ожиданием успеха.

### Сборка

Порядок фиксирован и не зависит от порядка добавления:

1. Безусловные объединения сжимают оси.
2. Безусловные «проверять по одному» (включая встроенное для параметров) заменяют входы группы составной осью размером 1 + Σ(nᵢ − 1). Вход в двух безусловных группах — ошибка.
3. Подсчёт строк формулой; больше 1 000 000 — отказ с разбивкой по входам. Сырое число без правил считается для воронки, но не перебирается.
4. Перебор.
5. Условные объединения.
6. «Нет родителя», «не вычисляется».
7. «Не бывает».
8. Условные «проверять по одному».
9. Сворачивание по порядку проверок.
10. «Не влияет» — объединение входов всех сработавших правил, кроме входов из их условий. Условия сверяются со строкой после шага 8.
11. Дедупликация по ключу.

**Потолок — 100 строк.** Выше — разбивка, какой вход сколько добавляет.

**Строка итога:**

| Поле | Содержание |
|---|---|
| `id` | стабильный, из хеша ключа (`r-3fa9`); в чате — номер по порядку и id |
| `name` | имя теста из человеческих названий: «регион больше максимума → 400 INVALID_REGION» |
| `setup` | записи в БД (поля по `key` и фактам), ответы моков, настройки, время, первый запрос (для повтора ключа) |
| `request` | метод, путь, заголовки, **тело сырым текстом**; по одному на каждый пример значения |
| `expect` | статус, заголовки, тело по шаблону |
| `calls` | ожидаемые вызовы с телом и числом раз |
| `writes` | ожидаемые записи и события |
| `must_not` | сервисы и сущности, которых строка не должна касаться (всё, чего нет в эффектах) |

Тело запроса собирается собственным сериализатором с «сырыми» вставками: дубль ключа, битый JSON, `1e2`, `-0`, большие числа сохраняют исходное написание.

### Назначение ответов

Агент ставит ответ строкам пачкой `[{outcome, rows, ref}]`; ссылка обязательна и проверяется; строки называются стабильными id. Назначение хранится по ключу и переживает пересборку. Строки «спека молчит» назначаются автоматически.

**Проверки назначений:**

| Проверка | Уровень |
|---|---|
| в строке «ошибка ввода», а ответ 2xx | предупреждение |
| все значения запроса, вызывающего и параметров — «норма», отказов нет, а ответ 4xx | предупреждение |
| сервис N сбоит, а в эффектах нет `call: N` | предупреждение |
| сервис N сбоит, а в эффектах есть вызов сервиса с большим `order` и он не в `skips` | предупреждение |
| сервис N сбоит после записи в БД в эффектах, а у записи нет `rollback` или `keep` | предупреждение «что стало с записью до сбоя?» |
| ответ при ретраях: `times` не совпадает с `retry` + 1 для «сбой на всех попытках» | предупреждение |
| текст по ссылке назначения не содержит ни статуса, ни кода | предупреждение |
| граничное и обычное значение одного входа дают разные ответы | информация |

Предупреждения агент показывает все. Информацию — сводкой.

### Ссылки

| Вид | Проверка |
|---|---|
| `file.md:§2.1` | раздел с номером **из текста заголовка** существует |
| `file:"текст"` | текст есть в файле |
| `file:line` | строка существует; при сдвиге ищется по содержимому и переякоривается |
| `file.json#/json/pointer` | указатель разрешается |
| `https://… "цитата"` | цитата обязательна; помечается «не проверена». Рекомендуется сохранить страницу в `.states/sources/` и ссылаться на файл |
| свободный текст | помечается «не проверена»; пустая — нет |

**Сверка факта со ссылкой.** Числа (`min`, `max`, `max_body`, `page_limit`, `retry`) ищутся в тексте по ссылке **как отдельные токены**: «100» не найдётся в «1000». Списки (`values`, `errors`, роли) — поэлементно. Не нашлось — предупреждение при показе входа. Пересказ словами («до ста символов») человек подтверждает вручную.

**Дрейф.** При принятии сущности скрипт запоминает отпечаток фрагмента по каждой её ссылке: раздел, цитату или строку по содержимому. Если фрагмент изменился или пропал — сущность снова «ждёт решения» с пометкой «источник изменился».

`status` всегда показывает долю непроверенных ссылок.

### Принятие и каскад сбросов

У ответов, входов (с их объединениями), правил, порядка проверок, чек-листа и матрицы есть статус **«ждёт решения» / «принято»**. Сборка применяет только принятое.

| Что изменилось | Что сбрасывается |
|---|---|
| вход, правило, порядок проверок | принятие матрицы; назначения живут, пока жив ключ строки; осиротевшие перечисляются |
| ответ | принятие матрицы; его строки помечаются «проверить», назначения остаются |
| источник по ссылке | сама сущность → «ждёт решения», дальше по этой же таблице |
| исходная модель у `copy_from` | ничего: копия независима |
| добавлен ответ на шаге 4 | только принятие матрицы; шаги не откатываются |

Матрицу нельзя принять при осиротевших назначениях и строках без ответа.

## Ход работы

| Шаг | Что происходит | Решения человека |
|---|---|---|
| **0 · Разведка** | агент читает материалы и отвечает на **чек-лист** скрипта: авторизация и роли, тенанты и владение, записи в БД и выборки, внешние сервисы и их порядок, ретраи, идемпотентность, флаги, зависимость от времени, лимиты размера. На каждый пункт — «есть» со ссылкой или «в материалах нет». Без ответа на все пункты входы заводить нельзя | 1: опись и чек-лист |
| **1 · Ответы и порядок** | каталог ответов; скрипт предлагает стандартные ответы для встроенных входов (битый JSON, 415, 413, 401, 403), если спека их упоминает; порядок проверок | 1–2 |
| **2 · Входы** | параметры запроса — **одной таблицей**, по строке на поле; вызывающий, БД, сервисы — по одному. Человеку показываются только отклонения: ловушки «влияет», добавки, предупреждения сверки, снятое по гарантии, «спека молчит», предложения объединить. Выведенное скриптом из сверенных фактов принимается по умолчанию | 3–5 |
| **3 · Правила** | только бизнес-специфика сверх встроенного, по одному, у каждого — эффект в строках | 0–3 |
| **4 · Матрица** | сборка, назначение ответов, разбор предупреждений и осиротевших назначений | 1 |
| **5 · Пробелы** | вопросы к аналитику: значения и строки «спека молчит», порядок проверок по умолчанию, недостижимые значения, непроверенные ссылки; проверки вне матрицы | — |

**Итог:** `.states/runs/<ручка>.json` со строками итога и `.states/runs/<ручка>.questions.md` — вопросы к аналитику.

## Инструменты MCP

Имена без префикса. Повторный вызов с тем же id перезаписывает запись (со сбросами по таблице), `remove: true` удаляет.

| Инструмент | Назначение |
|---|---|
| `init` | ручка, чек-лист, порядок проверок; добавляет встроенные входы |
| `outcome` | ответ |
| `input` | вход, несколько входов пачкой (для параметров) или `copy_from`; возвращает значения с классами и примерами, отклонения, предупреждения, число строк до и после |
| `rule` | правило; возвращает строк было и станет |
| `approve` | список сущностей или «матрица» |
| `build` | сборка |
| `assign` | пачка назначений; возвращает новые предупреждения |
| `rows` | строки по фильтру: без ответа, с предупреждением, по ответу, по входу; `full=true` — со всем содержимым строки итога |
| `status` | шаг, счётчики, «ждёт решения», предупреждения, непроверенные ссылки, чего не хватает |

**Запреты в коде:** входы до ответа на чек-лист; правило на несуществующий вход или значение; объединение значений разных классов; `assign` до `build`; принятие матрицы при осиротевших назначениях или строках без ответа.

**Формат ответов** — компактный JSON без markdown, колонки один раз, строки массивами, тексты человеческие. Все ошибки вызова — одним списком. Описания инструментов — 1–2 строки, подробности в SKILL.md.

```
{"ok":true,"input":"body.region","values":[["нет поля","ошибка ввода",[null]],["больше максимума","ошибка ввода",["aaa…(101)","ййй…(101)"]],["спека молчит","?",["​","  x  "]]],"rows":{"was":729,"now":810},"warnings":["в §2.1 нет числа 100"]}
{"ok":false,"errors":["чек-лист: нет ответа про «идемпотентность», «флаги»"]}
```

## Язык для пользователя

Всё, что видно в чате, — простыми словами.

| Внутри | В чате |
|---|---|
| `merge`, `irrelevant`, `independent`, `forbid` | «считать одинаковыми», «не влияет», «проверять по одному», «не бывает» — с объяснением в одну строку |
| классы значений | «норма», «ошибка ввода», «отказ», «спека молчит» |
| статусы | «ждёт твоего решения» / «принято» |
| пропуск в строке | «любое»; «нет родителя»; «не вычисляется» |
| id | строка — номер и короткий id; ответ — статус и код; правило — фразой |
| гарантия | «по схеме БД null не бывает — не проверяем» |
| инструменты, JSON, поля модели | никогда |

## Скилл (SKILL.md)

- шаги 0–5 с воротами «принято», формат «Шаг N из 5 · …»;
- перед вопросом показать всё, о чём спрашиваешь, таблицей, с отклонениями и счётчиками из `status`;
- вопросы всегда с вариантами; вопросы, на которые отвечает разработчик или аналитик, а не пользователь, не задавать — отправлять в шаг 5;
- `approve` — только после явного «да» в чате;
- предупреждения показывать все;
- никаких внутренних обозначений;
- отказ работать по коду сервиса.

## Эталонный пример: поиск ПВЗ

`POST /pvz/search` принимает `region`, `settlement`, `street`, `house`, склеивает через «, » и ищет ПВЗ через `GET /pvz?address=…` соседнего сервиса. Спека, контракт и точные числа воронки фиксируются в `examples/` и `test_engine` при реализации.

Ожидаемая форма:
- **входы:** запрос целиком; четыре поля; производный `len_concat(", ", поля)` против лимита сервиса ПВЗ; сервис ПВЗ (найден, не найден, 429, другая 4xx, 5xx, таймаут, нет соединения);
- **встроенное делает почти всё:** ошибки полей сворачивают сервис по порядку проверок; поля «проверять по одному»; при недопустимом поле производный вход «не вычисляется»;
- **правило одно:** «не влияет — при сбое сервиса значения полей не важны», условие «все поля — норма» задаётся классом;
- **строка «найден»:** запрос `{"region":"Московская область",…}`, ожидаемый вызов `GET /pvz?address=Московская область, Химки, Ленина, 5` один раз, тело ответа из примера контракта;
- **строка «длина больше лимита»:** примеры полей подобраны скриптом так, что склейка действительно длиннее лимита;
- **вопросы шага 5:** ответ клиенту при 4xx от ПВЗ; запятая внутри поля; «не найден» — 404 или пустой 200; обязательность `settlement`; значения «спека молчит» у полей.

## Что держится только на инструкции

- что «принято» сказал человек, а не агент;
- что агент показал данные и предупреждения полностью;
- что ссылка понята верно, а не только существует и содержит нужное число;
- что ответы на чек-лист разведки правдивы: входа, о котором агент не узнал, в матрице не будет.
