# state-matrix

Плагин Claude Code. Разбирает **спецификацию** на входные параметры, их значения
и состояния интерфейса, сворачивает матрицу по правилам из спеки и показывает
комбинации, о которых спека молчит.

Не генератор тестов: он ищет дыры, противоречия и недостижимые состояния.
Кода не читает намеренно — модель по реализации объявила бы текущие баги нормой.

## Установка

```bash
/plugin marketplace add https://github.com/Alexandr-Obraztsov/state-matrix
/plugin install state-matrix
```

Зависимостей нет: только `python3`. Ставить ничего не нужно.

## Как это выглядит

Дай агенту спеку и попроси построить матрицу состояний. Он проведёт через четыре
этапа, **останавливаясь на одобрение** перед каждым следующим:

| Шаг | Что происходит | Что спрашивает |
|---|---|---|
| **0. Поиск входов** | читает спеку и всё, на что она ссылается; проходит по источникам — ввод, навигация, ручки, сессия, окружение, время; **разматывает параметры ручек до источника** | «вот что нашёл» |
| **1. Параметры** | по одному показывает параметр со всеми значениями, объединениями и тем, откуда он приходит | по каждому: «всё верно?» |
| **2. Состояния** | справочник вариантов UI: показано, скрыто, грузится, пусто, ошибка, заблокировано | списком: «все варианты описаны?» |
| **3. Правила** | свёртка по зависимостям из спеки, по одному правилу | по каждому: «применить?» |
| **4. Матрица** | таблица целиком и случаи, о которых спека молчит | «что делать с непокрытым?» |

Всё общение в чате, коротко и таблицами. **Вопросы — всегда с вариантами
ответа**, чтобы можно было ничего не печатать. Каждое сообщение начинается
строкой вида `Шаг 1 из 4 · Параметры · 2 из 5`.

Агент показывает содержимое перед любым вопросом: результаты MCP-вызовов
в интерфейсе свёрнуты, пользователь их не видит.

## Тулы

| Тул | Что делает |
|---|---|
| `sm_cases` / `sm_learn` | корнер-кейсы по видам параметров; пополнение базы |
| `sm_init` | завести модель по спеке |
| `sm_param_add` / `sm_param_rm` | параметр целиком: описание, ссылка, все значения, объединение |
| `sm_exclude` | упомянутое, но не являющееся входом — с причиной |
| `sm_state_add` / `sm_state_rm` | состояние интерфейса: имя, что видно, ссылка |
| `sm_rule_add` / `sm_rule_rm` | правила свёртки матрицы |
| `sm_build` | собрать и напечатать матрицу |
| `sm_assign` | привязать состояние к строкам матрицы |
| `sm_rows` | строки матрицы, в том числе без состояния |

## База знаний по корнер-кейсам

`sm_cases` подсказывает, что обычно забывают у каждого вида параметра:

| вид | примеры корнер-кейсов |
|---|---|
| строка | пустая, только пробелы, эмодзи, длинное слово без пробелов, разметка внутри |
| число | ноль, граница и граница ±1, дробное там, где ждут целое, не передано |
| запрос | таймаут, пустой успешный ответ, частичные данные, ответ после ухода со страницы |
| права | 403 против 404, владелец против обычного, права отозваны в сессии |
| дата | граница суток, таймзона, переход на летнее время, 29 февраля |

Тринадцать видов с описаниями, 82 кейса, десять источников входов. Обращаться необязательно — это подсказки, а не
обязательный список.

**База пополняется.** Пользователь назвал подвох, которого не было, — `sm_learn`
дописывает его в `.states/knowledge.json`. Проектная часть коммитится
в репозиторий и переживает обновление плагина, так что инструмент со временем
узнаёт вашу предметную область.

MCP-сервер написан на голом stdio JSON-RPC — обёртка над теми же функциями, что
и CLI. Любой вызов повторяется руками через `scripts/sm.py` и даёт тот же вывод.

## Что делает строгим

- `sm_param_add` требует описание и ссылку на место в спеке
- `sm_param_add` требует перечислить **все** значения до объединения,
  а само объединение — объяснить ссылкой на спеку
- `sm_state_add` требует описание видимого и основание — откуда это взято
- `sm_rule_add` без подтверждённой ссылки правило не добавляет вовсе
- `sm_build` отказывает, пока нет параметров или не описано ни одного состояния
- основанием годится любой текст: раздел спеки, цитата, ссылка на Confluence
  или Jira. Но если сослались на файл репозитория — он и место в нём
  проверяются при записи, выдуманный раздел не пройдёт
- `validate.py` ловит модель, изменённую в обход тулов
- потолок 100 строк: превышение печатает вклад каждого параметра, а не «много»

## Вручную

```bash
S=scripts
M=.states/models/Checkout.states.json

python3 $S/sm.py init $M --system Checkout --source docs/checkout.md
python3 $S/sm.py param add $M --name cart --desc "Ответ на запрос корзины" \
        --from "docs/checkout.md:§2" \
        --all-values pending ok ok_empty error_network error_server \
        --values pending ok ok_empty error \
        --grouping "§2 описывает обе ошибки одинаково" --special timeout
python3 $S/sm.py state add $M --name "Загрузка" --desc "Скелетон формы" \
        --evidence "docs/checkout.md:§5"
python3 $S/sm.py build $M
python3 $S/sm.py assign $M --state "Загрузка" --rows r000
python3 $S/sm.py build $M
```

`python3 -m unittest discover -s tests` — 80 тестов плагина.
