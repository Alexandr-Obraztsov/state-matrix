# Корзина семантик

Корзина хранит не параметры, а **семантики** — повторяющиеся виды входов. У каждой
свой набор классов значений, спецзначений и обязательных вопросов.

Запись типа: **идентификатор, название, описание, вопросы с вариантами ответа**,
классы значений, спецзначения, типичные имена параметров.

## Зачем

Четыре эффекта, ради которых она существует:

1. **Одинаковые классы для одинаковых вещей.** `price` в одном месте и `cost`
   в другом тестируются одними значениями, а не теми, что пришли в голову.
2. **Вопросы не забываются.** Про таймаут у запроса спрашивается всегда, а не
   когда вспомнилось.
3. **Повторный прогон молчит.** Ответы лежат в модели; при следующей сборке
   они не переспрашиваются.
4. **Корзина учится.** Поправил пользователь — вопрос дописывается в тип
   и задаётся в следующий раз сам.

## Как искать

| Тул | Что возвращает |
|---|---|
| `sm_catalog_list` | идентификатор, название, описание — **без вопросов** |
| `sm_catalog_get` | карточку типа: все вопросы с вариантами, значения, имена |
| `sm_catalog` | подбор типа для параметра и первый вопрос |
| `sm_catalog_edit` | дополнить тип вопросом, именем, значением |
| `sm_catalog_new` | завести новый тип |

Список намеренно не показывает вопросы: восемнадцать типов по пять вопросов —
это девяносто строк, в которых ничего не видно. Вопросы приходят тогда, когда
тип уже выбран.

Совпадение ищется по имени параметра, затем по типу. Имена в корзине не
пересекаются между семантиками — иначе параметр ушёл бы не в ту корзину.

## Как корзина учится

Два случая, в которых её надо дополнить **сразу, не откладывая**:

**Пользователь поправил по существу** — значит в типе не хватало вопроса:

```
sm_catalog_edit(id="http_endpoint",
  add_questions=["cache=кэшируется ли ответ и как инвалидируется?|"
                 "да, с инвалидацией по событию|да, по времени|нет"])
```

**Тип не нашёлся по имени параметра** — добавь имя, чтобы в следующий раз нашёлся:

```
sm_catalog_edit(id="http_endpoint", add_names=["cart", "basket", "order"])
```

Правка ложится в проектную корзину `.states/catalog.json` и **дополняет**
дефолтную, а не заменяет: обновление плагина её не затрёт. Корзина коммитится
в репозиторий проекта, так что накопленное знание переживает смену сессии.

## Если тип не подошёл вовсе

```
sm_catalog_new(id="order_status", title="Статус заказа",
  desc="Позиция заказа в жизненном цикле. Ловушки — конечные статусы и возможность отката.",
  type="enum", names=["status", "orderState"],
  questions=["list=какие статусы существуют?|три|пять|заданы в спеке",
             "terminal=какие статусы конечные?|только cancelled|cancelled и delivered",
             "back=возможен ли возврат в предыдущий статус?|да|нет"],
  values=["new", "paid", "shipped", "cancelled"], special=["unknown_status"])
```

Название и описание обязательны: по ним тип выбирают из списка. Вопрос обязан
заканчиваться знаком вопроса. Варианты ответа пишутся через `|` после вопроса;
«в спеке не сказано» добавляется автоматически.

## Что в дефолтной корзине

**Данные:** `free_text`, `identifier`, `formatted_string`, `number`,
`money_amount`, `pagination_limit`, `percentage`, `duration`, `date_time`,
`collection`, `boolean_flag`

**Взаимодействие:** `http_endpoint`, `error_state`, `auth_role`, `file_upload`

**Окружение** (помечены `env_candidate`): `viewport`, `locale`, `feature_flag` —
эти обычно не меняются в рантайме, и их стоит выносить в `env`, а не умножать
на них матрицу.

## Спецзначения

`special` — значения, которые проверяются **по одному**, при остальных параметрах
в значениях по умолчанию, и не участвуют в декартовом произведении.

Так и надо: восемь спецзначений добавляют восемь строк вместо умножения матрицы
в 256 раз, а ловят почти столько же. Баг на `NaN` редко зависит от того, какая
рядом тема — светлая или тёмная.
