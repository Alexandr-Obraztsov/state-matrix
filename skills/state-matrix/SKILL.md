# State Matrix

Поднимает все состояния системы и требует описать исход каждого. Работает по коду
(`mode: code`) или по спеке (`mode: spec`).

## Железное правило

**Ты пишешь только `.states.yaml`.** Матрицу, достижимость, числа и отчёт считают
скрипты. Никогда не перечисляй комбинации в голове и не называй числа, которых
не напечатал `engine.py` — воспроизводимость держится именно на этом.

## Обязательный конвейер

Модель ты **не редактируешь руками**. Единственный способ её изменить —
`scripts/sm.py`. Он отказывает, когда протокол нарушен, и это не совет, а запрет.

```
extract.py                        кандидаты в параметры
   ↓
sm.py catalog <модель> <имя>      ОБЯЗАТЕЛЬНО перед каждым параметром
   ↓  отвечаешь на все вопросы семантики
sm.py param add   / sm.py exclude каждый кандидат — сюда или туда
   ↓
sm.py rule add                    правила для параметров
   ↓
sm.py state add                   именованные состояния из спеки
   ↓
sm.py build                       verify → validate → engine → отчёт
```

**Порядок жёсткий.** `param add` отказывает, если для этого имени не вызывали
`catalog`. `catalog` печатает обязательные вопросы семантики — `param add`
отказывает, пока на каждый нет `-a <вопрос>=…`. Ответ «неизвестно» допустим и
честен; молчание — нет. `rule add` без ссылки `file:line` ставит `assumed` и
требует `--ask`: вопрос человеку, который попадёт в отчёт с ценой в комбинациях.

Состояния (`sm.py state add`) — это **именованные состояния системы из спеки**:
«Загрузка», «Пустая корзина», «Приём файла». Каждое с условием на параметрах и
ссылкой. Движок раскладывает по ним строки матрицы. Строки, не попавшие ни в одно
состояние, остаются в таблице с пустой колонкой «состояние» — это и есть
непокрытые случаи, отдельного раздела для них не нужно.

Порядок состояний значим: побеждает первое подходящее.

## Когда отказываться

- Цель — модуль с десятком независимых состояний (`App.tsx` и подобные). Матрица
  взорвётся, и это диагноз: **предложи разбиение на подсистемы**, не строй модель.
- Проблема в порядке событий, времени или гонках за общий кусок состояния.
  Матрица этого не ловит. Скажи прямо и предложи property-based или model-based.
- Значения непрерывны и не сводятся к классам эквивалентности.

## Фазы

1. **Граница.** Что считаем системой. Если не одна — отказ с разбиением.
2. **Параметры.** Каждый со ссылкой `file:line` в `from`. Определи тип по тому,
   *что с параметром делают*, а не по аннотации.
3. **Окружение.** Параметры, которые не меняются в рантайме (версия контракта
   хоста, брейкпоинт, фича-флаг), помечай `env: true`. Они порождают отдельную
   матрицу на каждое значение, а не умножают одну. Без этого достижимость врёт.
4. **Значения.** Сверься с каталогом (`catalog/default.yaml` и `.states/catalog.yaml`).
   Совпала семантика — бери готовые классы, вопросов не задавай. Не совпала —
   пройди анкету типа и допиши семантику в проектный каталог.
5. **Ограничения.** `forbid` вычёркивает невозможные комбинации, `irrelevant`
   схлопывает незначащие колонки. У каждого — `evidence` и `status`.
   **Правило без доказательства — `assumed`, и оно не применяется к матрице.**
6. **Переходы.** `initial` + события. Без них достижимость не считается, и
   `UNREACHABLE` не отличить от `невозможно`.
7. **Прогон.** `validate.py` → `engine.py` → отчёт. Разбери вывод, заполни
   `outcomes`, повтори.

## Экономия вопросов

Черновая матрица строится **до** вопросов, на значениях из типов и схем.
Вопрос задаётся, только если ответ меняет матрицу — число строк или класс исхода.
Схлопнувшиеся параметры не обсуждаются: ответ про них ничего не поменяет.
Вопрос несёт догадку, `evidence` и цену незнания в комбинациях.

Человек отвечает **в HTML-отчёте**, а не в чате. Ответы ложатся в
`.states/answers.yaml`, следующий прогон их подхватывает.

## Команды

```bash
python3 scripts/validate.py <модель>
python3 scripts/engine.py <модель> -a .states/answers.yaml -o .states/runs/<имя>.json
python3 scripts/serve.py --data .states/runs/<имя>.json   # http://localhost:4177
```

## Классы находок

| Класс | Что значит |
|---|---|
| `UNDEFINED` | достижима, поведение не описано — основной улов |
| `UNREACHABLE` | валидна, но путь не ведёт — лишний параметр или забытый переход |
| `RULE_OVERLAP` | два правила применимы разом — порядок проверок не определён |
| `NONDET` | одно событие ведёт в разные состояния |
| `INVALID_EDGE` | переход ведёт в запрещённую комбинацию |
| `DEAD_END` | из состояния нет выхода |
| `MODEL_INCOMPLETE` | недостижимо больше половины — переходы описаны не полностью |
| `CEILING` | строк больше потолка — это не одна система |

`MODEL_INCOMPLETE` и `CEILING` блокируют разбор: сначала чини модель,
потом читай находки. Иначе утонешь в мусоре.
