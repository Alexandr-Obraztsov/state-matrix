# State Matrix

Разбирает **спецификацию** на входные параметры, их значения и состояния системы,
сворачивает матрицу по правилам из спеки и показывает, о чём спека молчит.

Инструмент работает только со спеками. Кода он не читает и не парсит: если
источник истины — реализация, матрица зафиксирует текущие баги как норму.

## Три железных правила

**1. Модель не редактируется руками.** Единственный вход — тулы `sm_*`.
Матрицу, достижимость и числа считают скрипты. Никогда не называй число,
которого не вернул `sm_build`.

**2. Ничего не выдумывать.** У каждого параметра, значения, правила и состояния
обязана быть ссылка на место в спеке или коде. Нет ссылки — не пиши правило,
а **скажи вслух, что источника нет**, и спроси пользователя. Выдуманное правило,
попавшее в матрицу, вычёркивает ровно те комбинации, которые никто не проверял.

**3. По одному вопросу за раз.** Никогда не вываливай список вопросов. Один
вопрос — 2–4 варианта ответа — следующий. Варианты бери из корзины
(`sm_catalog_get` печатает их у каждого вопроса) и дополняй тем, что увидел в
спеке. Последним вариантом всегда «в спеке не сказано»: это не отговорка,
а самая ценная находка — место, где спека молчит.

**4. Четверо ворот.** После каждого этапа — короткая сводка и один вопрос
с вариантами. Дальше не идти без ответа. Сводка **схематичная**: таблица без
прозы, чтобы понять за десять секунд.

## Порядок

```
спека → [1] параметры и значения  → ворота
      → [2] состояния системы     → ворота
      → [3] матрица + правила     → ворота
      → [4] исходы и отчёт        → ворота
```

Модель лежит в `.states/models/<Имя>.states.json`. Тулы подключаются вместе
с плагином; те же операции доступны через `${CLAUDE_PLUGIN_ROOT}/scripts/sm.py`,
если нужно повторить вызов руками при отладке.

## Этап 0. Завести модель

**`sm_init`** — `model`, `system`, `source` (путь к спецификации).

Прочитай спеку целиком и выпиши все входные параметры **до** того, как начнёшь
их добавлять. Полноту списка машина проверить не может — её подтверждает человек
на первых воротах, поэтому список должен быть исчерпывающим, а не первым пришедшим
в голову.

Упомянутое в спеке, но не являющееся параметром, отправляй в **`sm_exclude`**
с причиной — так видно, что оно рассмотрено, а не забыто.

## Этап 1. Параметры и их значения

Для **каждого** параметра, найденного в спеке, по очереди:

**1.1 — корзина.** Обязательный первый шаг: **`sm_catalog`** (`model`, `name`,
`type`). Без него `sm_param_add` откажет. Он вернёт название типа, его описание
и первый вопрос; остальные вопросы с вариантами — **`sm_catalog_get`**.

Выбор типа тоже показывай вариантами: **`sm_catalog_list`** даёт список
«идентификатор — название — описание» без вопросов, чтобы не перегружать.

Возвращает подходящую семантику, её классы значений и обязательные вопросы.
Тип определяй по тому, *что с параметром делают*: `string` бывает
идентификатором, ссылкой, markdown или свободным текстом — четыре разные
семантики с разными вопросами.

Если по имени не определилось, тул печатает всех кандидатов по типу — выбери
сам и передай `catalog: <id>` в `sm_param_add`. Ничего не подошло — заведи тип через **`sm_catalog_new`**: нужны идентификатор,
**название**, **описание** и вопросы с вариантами
([references/catalog.md](references/catalog.md)).

**1.2 — ответить на вопросы, по одному.** Порядок поиска ответа:

| Источник | Что делать |
|---|---|
| схема или тип | брать как есть, это доказательство |
| спека | цитировать, ссылку в `--from` |
| ничего | **сказать пользователю, что источника нет, и спросить** |

Сначала ответь сам на всё, что нашёл в спеке, — молча, не спрашивая. Оставшиеся
вопросы задавай **по одному**, каждый с вариантами:

```
Сумма: в каких единицах?
  • копейки
  • рубли
  • в спеке не сказано
```

Получил ответ — запиши и переходи к следующему вопросу. Не пиши `неизвестно`
молча: это допустимо, только если человек сам выбрал «в спеке не сказано».

**Если пользователь ответил не вариантом, а поправил тебя по существу** — значит
в типе не хватало вопроса. Добавь его в корзину через **`sm_catalog_edit`**
(`add_questions: ["id=текст вопроса?|вариант|вариант"]`), и в следующий раз он
задастся сам. То же, когда параметр не нашёлся по имени: добавь имя через
`add_names`, чтобы тип определялся автоматически.

**1.3 — перечислить ВСЕ значения, потом объединять.**

Сначала выпиши из спеки **все возможные значения** параметра, без обобщений.
Если спека различает `error_network` и `error_server` — это два значения, даже
если обрабатываются одинаково.

Затем реши, какие из них ведут себя **одинаково с точки зрения исхода**, и
объедини в классы. Объединение всегда требует основания из спеки, и его надо
показать пользователю до того, как записывать:

```
cart: нашёл 5 значений — pending, ok, ok_empty, error_network, error_server

Предлагаю объединить error_network и error_server в один класс error:
§2 описывает их одинаково — заглушка с кнопкой «Повторить».

  • объединить, как предложено
  • оставить раздельно
  • объединить иначе
```

Согласие получено — записывай. Отказался — значения остаются раздельными.

**1.4 — добавить: `sm_param_add`**

`model`, `name`, `type`, **`all_values`** (все найденные значения),
**`values`** (классы после объединения), **`grouping`** (почему объединили —
обязателен, если классов меньше, чем значений), `special`, `from`, `desc`,
`answers`, `env: true` для параметров, не меняющихся в рантайме.

Тул откажет, если `all_values` не заданы или если объединение не объяснено.

### Ворота 1

Одна таблица и один вопрос с вариантами — «всё верно» / «не хватает параметра» /
«значения не те»:

```
параметр   тип        значений  классов  объединение          источник
cart       endpoint   5         4        error_* → error      §2
amount     money      4         4        —                    §3
promo      enum       3         3        —                    §4
viewport   enum       3         3        —                    §1

без ответа в спеке: максимальная длина комментария, поведение при офлайне
```

**Дальше не идти без ответа.**

## Этап 2. Состояния системы

Именованные состояния **из спеки**: «Загрузка», «Пустая корзина», «Ошибка сети».
Не выдумывать: если состояние не названо в спеке — это вопрос пользователю.

**`sm_state_add`**: `name`, `when` (список `параметр=значение`), `desc`, `evidence`.

Порядок значим: побеждает первое подходящее, поэтому частные случаи раньше общих.

### Ворота 2

```
состояние            условие                     источник
Загрузка             cart=pending                Спека §3.1
Пустая корзина       cart=empty                  Спека §3.2
Ошибка сети          cart=error                  Спека §3.4
Оформление           cart=ok                     Спека §4

в спеке не описано: что при cart=ok и amount=0
```

Один вопрос с вариантами: «список полон» / «не хватает состояния» /
«условие неверно». **Дальше не идти без ответа.**

## Этап 3. Матрица и правила свёртки

Собрать: **`sm_build`** (`model`, `root`).

Если строк больше **100** — матрица не готова. Ищи правила **в спеке**, а не в
голове. Два вида:

**`sm_rule_add`** двух видов:

- **запрет** — `forbid: ["auth=guest", "promo=valid,expired"]`: комбинация
  невозможна, строки вычёркиваются;
- **схлопывание** — `when: ["cart=pending"]` + `irrelevant: ["promo", "amount"]`:
  значения не влияют на исход, колонки сливаются в «∗».

Обоим обязательны `evidence` и `desc`.

Правило без ссылки получает статус `assumed`, **не применяется к матрице** и
требует `--ask` — вопрос человеку одной фразой. Это единственная защита от
«ужму матрицу, чтобы красиво было».

Параметр, который не меняется ни одним переходом, — кандидат в **окружение**
(`env: true`): он не умножает матрицу, а делит её на срезы. `build` при превышении
потолка сам печатает вклад каждого параметра и называет таких кандидатов.

Не проси поднять потолок. Если после всех правил из спеки строк больше ста —
**это несколько систем в одном документе**, и правильный ответ: предложить
разбиение.

### Ворота 3

```
648 комбинаций → 210 после запретов → 40 строк

правила свёртки:
  запрет       гость + промокод невозможны        Спека §5      −120
  схлопывание  при загрузке поля не важны         Спека §3.1    ×24 → 1
  окружение    viewport не меняется в рантайме    Спека §1      3 среза

не подтверждено спекой (в матрицу не пошло):
  ? в офлайне форма скрывается или блокируется — затрагивает 16 комбинаций
```

Неподтверждённые правила выноси **по одному**, каждое с вариантами
«подтвердить» / «опровергнуть» / «переформулировать». Ответ записывай через
**`sm_answer`** сразу, не копя. **Дальше не идти без ответа.**

## Этап 4. Исходы и отчёт

Разобрать строки без состояния:

**`sm_rows`** с `no_state: true` по файлу `.states/runs/<Имя>.json`.

По каждой решить: описать новое состояние (со ссылкой на спеку) или признать
комбинацию невозможной и завести `forbid`. Если ни то ни другое — **это дыра
в спеке**, она идёт в отчёт.

Пересобрать через **`sm_build`** и напечатать отчёт **целиком**.

### Ворота 4

Отчёт печатается как есть, без пересказа: параметры → исключённые → правила →
состояния → матрица → спецзначения → находки → требует уточнения. После него —
три строки своими словами: что не учтено, что нужно дозаполнить в спеке, какая
матрица получилась.

## Когда отказываться

- Дали код, а не спеку: скажи, что читаешь только спецификации. Модель по коду
  зафиксировала бы текущее поведение как правильное — включая баги.
- Цель — документ на десяток независимых подсистем: предложи разбиение.
- Проблема в порядке событий, времени или гонках: матрица этого не ловит,
  скажи прямо и предложи property-based тесты.
- Значения непрерывны и не сводятся к классам эквивалентности.

Классы находок — [references/findings.md](references/findings.md).
