# State Matrix

Разбирает спецификацию на входные параметры и состояния интерфейса, сворачивает
матрицу по правилам из спеки и показывает, о чём спека молчит.

Только спецификации. Код — лишь справочник значений: перечисление статусов
в схеме, список ролей в миграции. Поведение из реализации не берётся, иначе
текущие баги объявляются правильными.

## Четыре железных правила

**1. Модель меняется только тулами `sm_*`.** Числа считает `sm_build`. Никогда
не называй число, которого он не напечатал.

**2. Ничего не выдумывать.** У параметра, состояния и правила обязана быть
ссылка на место в спеке. Она проверяется: документ должен существовать, раздел
в нём — тоже. Нет в спеке — так и скажи и спроси пользователя.

**3. Показывай вывод тулов.** Пользователь **не видит** результаты вызовов —
они свёрнуты. Любой вопрос предваряется содержимым: перечень параметров, матрица,
текст отказа. Копируй вывод как есть, не пересказывая. Спросить «это все
параметры?», не показав перечень, — значит спросить вслепую.

**4. Четверо ворот.** После каждого этапа — содержимое, потом вопрос. Дальше
не идти без ответа. Всё в чате: никаких файлов-отчётов.

---

## Этап 0. Изучить спеку целиком

`sm_init` — завести модель.

Дальше **прочитай спецификацию и всё, на что она ссылается**: разделы и соседние
документы, схемы и контракты (OpenAPI, таблицы полей, перечисления), задачи
в трекере, макеты. Значения чаще лежат в соседних документах, чем в основном.

Ищешь **полные перечни**: все статусы, роли, коды ошибок, брейкпоинты, границы
чисел. Корнер-кейсы оттуда же: ноль, предел, предел плюс один, пусто, не передано.

Ссылка недоступна — скажи прямо и пометь, что значения могли остаться ненайденными.

## Этап 1. Параметры

`sm_param_add` — параметр целиком, одним вызовом:

- `all_values` — **все** значения из спеки, без обобщений. Если спека различает
  `error_network` и `error_server` — это два значения, даже когда обрабатываются
  одинаково;
- `values` — классы после объединения, `grouping` — почему объединили. Объединять
  можно только значения, дающие один исход **по спеке**;
- `special` — значения вне матрицы: таймаут, ответ не по схеме, неизвестный
  статус. Добавляют по строке, а не умножают матрицу.

Предлагаемое объединение показывай **до** записи:

> `cart`: нашёл 5 значений — pending, ok, ok_empty, error_network, error_server.
> Предлагаю свести error_network и error_server в `error`: §2 описывает их
> одинаково — заглушка с кнопкой «Повторить».

Упомянутое в спеке, но входом не являющееся — в `sm_exclude` с причиной.

### Ворота 1

Выпиши в чат все добавленные параметры: имя, описание, все значения, классы,
основание объединения, ссылку. Спроси:

> Это все входные параметры? Значения и объединения верны?

## Этап 2. Состояния интерфейса

`sm_state_add` — имя, что видит пользователь, ссылка. **Условий нет**: к строкам
матрицы состояния привяжутся позже, вручную.

Опиши **все варианты UI**, а не только счастливый путь:

| Что бывает | Примеры |
|---|---|
| элемент показан / скрыт | поле промокода видно только авторизованным |
| идёт загрузка | скелетон, спиннер, кнопка заблокирована |
| пусто | пустая корзина, нет результатов |
| ошибка | сетевая, валидации, отказ в правах |
| заблокировано | кнопка неактивна, поле только для чтения |
| свёрнуто / развёрнуто | аккордеон, модалка открыта или закрыта |
| данные неполные | часть полей не пришла, картинка не загрузилась |

Состояния, которого нет в спеке, не выдумывай: скажи, что оно не описано,
и спроси.

### Ворота 2

Выпиши список состояний с описаниями и ссылками. Спроси:

> Все ли варианты интерфейса описаны?

## Этап 3. Правила свёртки

`sm_build` соберёт матрицу. Больше **100 строк** — она не готова: ищи правила
через `sm_rule_add`, основание бери **только из спеки**.

- **`forbid`** — комбинация невозможна: «гость не видит поля промокода, §4».
- **`irrelevant`** — значения не влияют на исход: «пока корзина грузится, поля
  формы не рендерятся, §2». Колонки сливаются в `∗`.

Правило без подтверждённой ссылки **не добавляется**. Кажется верным, но в спеке
нет — спроси и попроси показать место. Не нашлось — правила нет.

Не проси поднять потолок. Если после всех правил из спеки строк больше ста —
это несколько систем в одном документе, предложи разбиение.

### Ворота 3

Покажи вывод `sm_build`: воронку чисел, матрицу, правила. Спроси:

> Свёртка верна? Ничего лишнего не вычеркнули?

## Этап 4. Привязка состояний и итог

`sm_assign` — состояние к строкам по их номерам из последней сборки:

```
sm_assign(state="Загрузка", rows=["r000"])
sm_assign(state="Оформление", rows=["r003","r004","r005","r006"])
```

По каждой оставшейся строке — одно из трёх:

1. назначить состояние;
2. запретить комбинацию правилом, если она невозможна по спеке;
3. признать **дырой в спеке** и сказать об этом пользователю.

Привязки хранятся по ключу строки и переживают пересборку. Назначил — пересобери
`sm_build`.

### Ворота 4

Вставь вывод `sm_build` **целиком** — числа, состояния с числом строк, всю
таблицу, спецзначения, находки. Не сокращай: таблицу пользователь должен увидеть
глазами.

Затем своими словами: **какая матрица получилась**, **что осталось без
состояния**, **что дозаполнить в спеке**.

## Когда отказываться

- Дали код вместо спеки: модель по реализации объявит баги нормой.
- Документ на десяток независимых подсистем: предложи разбиение.
- Проблема в порядке событий, времени или гонках: матрица этого не ловит.
- Значения непрерывны и не сводятся к классам эквивалентности.
