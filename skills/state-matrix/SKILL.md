# State Matrix

Разбирает спецификацию на входные параметры, их значения и состояния интерфейса,
сворачивает матрицу по правилам из спеки и показывает, о чём спека молчит.

Только спецификации. Код читается лишь как справочник значений — перечисление
статусов в схеме, список ролей в миграции. Поведение из реализации не берётся:
это объявило бы текущие баги правильными.

## Три железных правила

**1. Модель меняется только тулами `sm_*`.** Числа считают скрипты. Никогда не
называй число, которого не вернул `sm_build`.

**2. Ничего не выдумывать.** У параметра, значения, правила и состояния обязана
быть ссылка на место в спеке. Нет ссылки — так и скажи: «в спеке этого нет»,
и спроси. Выдуманное правило вычёркивает из матрицы ровно те комбинации,
которые никто не проверял.

**3. Четверо ворот.** После каждого этапа — компактная сводка и вопрос.
Дальше не идти без ответа. Всё общение в чате: никаких файлов-отчётов.

## Этап 0. Изучить спеку целиком

`sm_init` — завести модель.

Дальше **прочитай спецификацию и всё, на что она ссылается**, прежде чем что-то
объявлять. Значения параметров чаще лежат в соседних документах, чем в основном:

- ссылки внутри спеки — на разделы, документы, схемы, макеты;
- задачи в трекере (Jira, Linear, GitHub Issues), если спека на них ссылается;
- схемы и контракты: OpenAPI, таблицы полей, перечисления в базе, примеры ответов;
- соседние спеки той же системы — статусы и роли обычно описаны один раз;
- код — **только за перечнями значений**, не за поведением.

Ищешь: полные перечни. Все статусы, все роли, все коды ошибок, все брейкпоинты,
все границы чисел. Корнер-кейсы — оттуда же: предельные значения, пустые,
отсутствующие, неизвестные с бэкенда.

Ссылка недоступна — скажи прямо и пометь, что значения могли остаться ненайденными.

## Этап 1. Все входные параметры

Объяви **сразу все** параметры, какие нашёл: `sm_param_add` по каждому — имя, тип,
описание одной фразой, ссылка на спеку. Значения пока не задавай.

Упомянутое в спеке, но входом не являющееся — в `sm_exclude` с причиной. Так
видно, что рассмотрено, а не забыто.

### Ворота 1

`sm_params` печатает перечень. Покажи его и спроси прямо:

> Это все входные параметры системы? Чего-то не хватает?

Не переходи к значениям, пока не подтвердят. Добавился параметр — вернись сюда
и покажи перечень заново.

## Этап 2. Значения каждого параметра

Теперь по одному параметру, `sm_param_values`:

**Сначала `all_values` — все значения из спеки, без обобщений.** Если спека
различает `error_network` и `error_server` — это два значения, даже когда
обрабатываются одинаково. Сюда же корнер-кейсы: ноль, предел, предел плюс один,
пусто, не передано.

**Потом `values` — классы после объединения, и `grouping` — почему.** Объединять
можно только значения, дающие **один и тот же исход по спеке**. Основание
показывай пользователю до записи:

> `cart`: нашёл 5 значений — pending, ok, ok_empty, error_network, error_server.
> Предлагаю свести error_network и error_server в один класс `error`:
> §2 описывает их одинаково — заглушка с кнопкой «Повторить».

**`special` — значения, проверяемые по одному, вне матрицы.** Таймаут, ответ не
по схеме, неизвестный статус с бэкенда. Они добавляют по строке, а не умножают
матрицу: баг на таймауте не зависит от того, какой рядом брейкпоинт.

Тул откажет, если `all_values` не заданы или объединение не объяснено.

### Ворота 2

`sm_show` печатает модель со значениями. Покажи и спроси:

> Значения и объединения верны?

## Этап 3. Состояния интерфейса

`sm_state_add` по каждому состоянию: название, условие на параметрах, что
пользователь видит, ссылка на спеку.

**Покрыть надо все варианты UI, а не только счастливый путь.** Пройдись по списку:

| Что бывает | Примеры |
|---|---|
| элемент показан / скрыт | поле промокода видно только авторизованным |
| идёт загрузка | скелетон, спиннер, кнопка заблокирована |
| пусто | пустой список, пустая корзина, нет результатов |
| ошибка | сетевая, валидации, отказ в правах |
| заблокировано | кнопка неактивна, поле только для чтения |
| свёрнуто / развёрнуто | аккордеон, модалка открыта или закрыта |
| данные неполные | часть полей не пришла, картинка не загрузилась |

Порядок значим: побеждает первое подходящее состояние, поэтому частные случаи
ставь раньше общих. Состояние без условия — запасное, только последним.

Состояние, которого нет в спеке, не выдумывай: скажи, что комбинация не описана,
и спроси, как должно быть.

### Ворота 3

`sm_states` печатает список по порядку. Покажи и спроси:

> Все ли варианты интерфейса описаны? Порядок верный?

## Этап 4. Правила и матрица

`sm_build` соберёт матрицу. Больше **100 строк** — она не готова: ищи правила
свёртки через `sm_rule_add`, но основание бери **только из спеки**.

- **`forbid`** — комбинация невозможна: «гость не видит поля промокода, §4».
- **`irrelevant`** — значения не влияют на исход: «пока корзина грузится, поля
  формы не рендерятся, §2».
- **`env`** у `sm_param_add` — параметр не меняется в рантайме: делит матрицу
  на срезы, а не умножает её.

Спека описывает последовательность — добавь переходы через `sm_transition_add`:
тогда движок посчитает достижимость и отличит «сюда не попасть» от «не описано».

Правило без ссылки получает статус `assumed`, в матрицу не идёт и требует `ask` —
вопроса пользователю. Неподтверждённые выноси **по одному**, ответ записывай
`sm_answer` сразу.

Строки без состояния разбирай через `sm_rows` с `no_state`: по каждой либо новое
состояние со ссылкой, либо `forbid`, либо — если ни то ни другое — это дыра
в спеке, и она идёт в ответ пользователю.

Не проси поднять потолок. Если после всех правил из спеки строк больше ста —
это несколько систем в одном документе, предложи разбиение.

### Ворота 4

Покажи вывод `sm_build` целиком — сводку, состояния с числом строк, матрицу,
спецзначения, находки. Не пересказывай: числа должны быть те, что напечатал тул.

Затем три вещи своими словами: **что не покрыто**, **что нужно дозаполнить
в спеке**, **какая матрица получилась**.

## Когда отказываться

- Дали код вместо спеки: объясни, что модель по реализации объявит баги нормой.
- Документ на десяток независимых подсистем: предложи разбиение.
- Проблема в порядке событий, времени или гонках: матрица этого не ловит.
- Значения непрерывны и не сводятся к классам эквивалентности.
