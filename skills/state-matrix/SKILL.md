# State Matrix

Разбирает спецификацию (или код) на входные параметры, их значения и состояния
системы, сворачивает матрицу по правилам из спеки и показывает, о чём спека молчит.

## Три железных правила

**1. Модель не редактируется руками.** Единственный вход — тулы `sm_*`.
Матрицу, достижимость и числа считают скрипты. Никогда не называй число,
которого не вернул `sm_build`.

**2. Ничего не выдумывать.** У каждого параметра, значения, правила и состояния
обязана быть ссылка на место в спеке или коде. Нет ссылки — не пиши правило,
а **скажи вслух, что источника нет**, и спроси пользователя. Выдуманное правило,
попавшее в матрицу, вычёркивает ровно те комбинации, которые никто не проверял.

**3. Четверо ворот.** После каждого этапа — короткая сводка и вопрос «так?».
Не переходи дальше без ответа. Сводка **схематичная**: таблица или список,
без прозы. Пользователь должен понять за десять секунд.

## Порядок

```
спека → [1] параметры и значения  → ворота
      → [2] состояния системы     → ворота
      → [3] матрица + правила     → ворота
      → [4] исходы и отчёт        → ворота
```

Модель лежит в `.states/models/<Имя>.states.json`. Тулы подключаются вместе
с плагином; те же операции доступны через `${CLAUDE_PLUGIN_ROOT}/scripts/sm.py`,
если нужно повторить вызов руками при отладке.

---

## Этап 0. Завести модель

**`sm_init`** — `model`, `system`, `source`, `mode`.
`mode: spec` — разбор спецификации, `mode: code` — разбор существующего кода.

Для кода дополнительно **`sm_extract`**: каждый кандидат из вывода обязан стать
либо параметром, либо уйти в **`sm_exclude`** с причиной.

## Этап 1. Параметры и их значения

Для **каждого** параметра, найденного в спеке, по очереди:

**1.1 — корзина.** Обязательный первый шаг: **`sm_catalog`** (`model`, `name`,
`type`). Без него `sm_param_add` откажет.

Возвращает подходящую семантику, её классы значений и обязательные вопросы.
Тип определяй по тому, *что с параметром делают*: `string` бывает
идентификатором, ссылкой, markdown или свободным текстом — четыре разные
семантики с разными вопросами.

Если по имени не определилось, тул печатает всех кандидатов по типу — выбери
сам и передай `catalog: <id>` в `sm_param_add`. Ничего не подошло — заведи
семантику через **`sm_catalog_new`** ([references/catalog.md](references/catalog.md)).

**1.2 — ответить на вопросы.** Порядок поиска ответа:

| Источник | Что делать |
|---|---|
| схема или тип | брать как есть, это доказательство |
| спека | цитировать, ссылку в `--from` |
| код (в режиме `spec`) | **не ответ**, а новый вопрос: «код делает так, спека молчит — намеренно?» |
| ничего | **сказать пользователю, что источника нет, и спросить** |

Не пиши `неизвестно` молча. `неизвестно` допустимо, только если человек ответил,
что не знает.

**1.3 — добавить: `sm_param_add`**

`model`, `name`, `type`, `values`, `special`, `from` (ссылка вида `file.ts:27`
или `docs/spec.md:§3`), `desc`, `answers` — список `вопрос=ответ` по каждому
вопросу семантики, `env: true` для параметров, не меняющихся в рантайме.

### Ворота 1

Показать таблицей и спросить:

```
параметр     тип        значения                  источник
cart         endpoint   pending/ok/empty/error    Спека §3.1
amount       money      0/1коп/обычная/>лимита    Спека §4 «Лимиты»
promo        enum       нет/валидный/истёкший     Спека §5
viewport     enum       mobile/tablet/desktop     ← нет в спеке, спросил

без ответа в спеке: максимальная длина комментария, поведение при офлайне
```

Спросить: параметры и значения верны? чего-то не хватает?
**Дальше не идти без ответа.**

## Этап 2. Состояния системы

Именованные состояния **из спеки**: «Загрузка», «Пустая корзина», «Ошибка сети».
Не выдумывать: если состояние не названо в спеке — это вопрос пользователю.

**`sm_state_add`**: `name`, `when` (список `параметр=значение`), `desc`, `evidence`.

Порядок значим: побеждает первое подходящее, поэтому частные случаи раньше общих.

### Ворота 2

```
состояние            условие                     источник
Загрузка             cart=pending                Спека §3.1
Пустая корзина       cart=empty                  Спека §3.2
Ошибка сети          cart=error                  Спека §3.4
Оформление           cart=ok                     Спека §4

в спеке не описано: что при cart=ok и amount=0
```

Спросить: список состояний полон? **Дальше не идти без ответа.**

## Этап 3. Матрица и правила свёртки

Собрать: **`sm_build`** (`model`, `root`).

Если строк больше **100** — матрица не готова. Ищи правила **в спеке**, а не в
голове. Два вида:

**`sm_rule_add`** двух видов:

- **запрет** — `forbid: ["auth=guest", "promo=valid,expired"]`: комбинация
  невозможна, строки вычёркиваются;
- **схлопывание** — `when: ["cart=pending"]` + `irrelevant: ["promo", "amount"]`:
  значения не влияют на исход, колонки сливаются в «∗».

Обоим обязательны `evidence` и `desc`.

Правило без ссылки получает статус `assumed`, **не применяется к матрице** и
требует `--ask` — вопрос человеку одной фразой. Это единственная защита от
«ужму матрицу, чтобы красиво было».

Параметр, который не меняется ни одним переходом, — кандидат в **окружение**
(`env: true`): он не умножает матрицу, а делит её на срезы. `build` при превышении
потолка сам печатает вклад каждого параметра и называет таких кандидатов.

Не проси поднять потолок. Если после всех правил из спеки строк больше ста —
**это несколько систем в одном документе**, и правильный ответ: предложить
разбиение.

### Ворота 3

```
648 комбинаций → 210 после запретов → 40 строк

правила свёртки:
  запрет       гость + промокод невозможны        Спека §5      −120
  схлопывание  при загрузке поля не важны         Спека §3.1    ×24 → 1
  окружение    viewport не меняется в рантайме    Спека §1      3 среза

не подтверждено спекой (в матрицу не пошло):
  ? в офлайне форма скрывается или блокируется — затрагивает 16 комбинаций
```

Спросить: правила верны? неподтверждённые — подтвердить или опровергнуть?
**Дальше не идти без ответа.**

## Этап 4. Исходы и отчёт

Разобрать строки без состояния:

**`sm_rows`** с `no_state: true` по файлу `.states/runs/<Имя>.json`.

По каждой решить: описать новое состояние (со ссылкой на спеку) или признать
комбинацию невозможной и завести `forbid`. Если ни то ни другое — **это дыра
в спеке**, она идёт в отчёт.

Пересобрать через **`sm_build`** и напечатать отчёт **целиком**.

### Ворота 4

Отчёт печатается как есть, без пересказа: параметры → исключённые → правила →
состояния → матрица → спецзначения → находки → требует уточнения. После него —
три строки своими словами: что не учтено, что нужно дозаполнить в спеке, какая
матрица получилась.

## Когда отказываться

- Цель — документ на десяток независимых подсистем: предложи разбиение.
- Проблема в порядке событий, времени или гонках: матрица этого не ловит,
  скажи прямо и предложи property-based тесты.
- Значения непрерывны и не сводятся к классам эквивалентности.

Классы находок — [references/findings.md](references/findings.md).
